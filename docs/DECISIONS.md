# Decisions

Formato: data · decisione · alternative scartate · motivo.

Le decisioni sono in inglese (documentazione tecnica, regola 1.7 di CLAUDE.md); questa intestazione resta in italiano per il committente.

## 2026-10-01 · Reference repositories location

**Decision.** The two reference codebases were found already cloned next to this repository, outside it: `/home/user/lorena-control-center` (Control Room / Command Center) and `/home/user/rehaus-ops-studio-533b1b8f` (Rehaus). They were studied read-only; nothing was copied, no `.env` was opened.

**Alternatives.** Cloning them again from GitHub (unnecessary: identical content).

## 2026-10-01 · PostgreSQL 16 from the system package instead of Docker

**Decision.** The cloud session has the Docker CLI but no Docker daemon. PostgreSQL 16.14 is installed as an Ubuntu package, so development and tests run against a local cluster on `127.0.0.1:5432` (`postgres`/`postgres`, databases `hullwise` and `hullwise_test`). `docker-compose.yml` stays in the repository and is the default for local machines: only `DATABASE_URL` changes.

**Alternatives.** PGlite or `embedded-postgres` (rejected: PGlite does not support `pg-boss` and multiple connections with session-level `SET` reliably; a real Postgres keeps RLS behaviour identical to production).

## 2026-10-01 · Pinned stack versions

**Decision.** `next@15.5` (CLAUDE.md fixes Next 15; Next 16 is available but out of brief), `react@19`, `typescript@5.9` (TypeScript 7 is available but its native compiler is not yet supported by every tool in the chain), `eslint@9` with `typescript-eslint@8` and `eslint-config-next@15`, `tailwindcss@4`, `next-intl@4`, `next-auth@5 beta` (Auth.js), `drizzle-orm@0.45` + `drizzle-kit@0.31`, `pg-boss@12`, `vitest@3`, `@playwright/test@1.63`, `turbo@2`, `pnpm@10`.

**Alternatives.** Latest majors across the board (rejected: three breaking majors on day one would cost phase 0 without product value).

## 2026-10-01 · shadcn/ui components written by hand in `packages/ui`

**Decision.** The shared UI package contains hand-written shadcn-style components (Radix primitives + Tailwind + `cva`) rather than components generated by the shadcn CLI. Same API shape, so a future `shadcn add` keeps working.

**Alternatives.** Running the shadcn CLI (rejected: interactive, registry fetches at build time, and it writes into `apps/web` instead of a shared package).

## 2026-10-01 · Two database roles, one setting

**Decision.** `hullwise_admin` owns the schema, runs migrations, the seed, pg-boss and the super-admin console (`BYPASSRLS`). `hullwise_app` is the only role the tenant-facing application uses; every domain table has `ENABLE ROW LEVEL SECURITY` and a policy `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid`. `withTenant(tenantId, fn)` opens a transaction and calls `set_config('app.tenant_id', …, true)` so the value dies with the transaction and can never leak through the pool. An unset setting yields no rows rather than an error.

**Alternatives.** One role with `SET ROLE` per request (rejected: a forgotten reset leaks); schema-per-tenant (rejected: migrations × tenants, and the brief asks for RLS).

## 2026-10-01 · Platform tables vs domain tables

**Decision.** `users`, `accounts`, `sessions`, `verification_tokens`, `tenants`, `tenant_memberships`, `tenant_addons` are platform tables without RLS, read through the admin connection by the authentication layer only (resolve who the user is and which tenants they may open). Everything else carries `tenant_id` and RLS. `audit_logs` is tenant-readable and append-only for the app role.

## 2026-10-01 · Locale without URL prefix

**Decision.** next-intl runs without locale routing: the locale comes from the `NEXT_LOCALE` cookie, written at sign-in from the user's preference (fallback: tenant default) and by the language picker. URLs stay `/t/<tenant>/orders` in every language, which keeps links shareable across a team that speaks different languages.

**Alternatives.** `/[locale]/…` routing (rejected: the same order would have three URLs, and the tenant slug already occupies the first segment).

## 2026-10-01 · Tenant in the URL

**Decision.** Tenant pages live under `/t/<slug>/…`; the super-admin console under `/admin`. A user with several memberships switches tenant by changing the slug. The membership check happens server-side on every request; the tenant id is never taken from a cookie.

## 2026-10-01 · Auth.js with JWT sessions

**Decision.** Credentials (bcrypt) + magic link (link printed to the console in development, `MAGIC_LINK_WEBHOOK_URL` for a real mailer) with the Drizzle adapter for verification tokens and JWT sessions (Credentials requires JWT). Memberships are not stored in the token: they are read per request so a role change is effective immediately.

## 2026-10-01 · Isolation tests are generated from the schema, not written per table

**Decision.** `packages/db/test/isolation.test.ts` enumerates every Drizzle table with a `tenant_id` column and runs the same six checks on each (RLS enabled with a policy, seed covers both tenants, no cross-tenant read, no cross-tenant update/delete, cross-tenant insert rejected with `42501`, nothing visible without context). A new domain table is covered the moment it is exported from the schema; a table without `tenant_id` fails the suite unless listed as a platform table. The seed must populate both tenants, which keeps the demo data honest too.

**Alternatives.** Hand-written tests per table (rejected: they rot, and a forgotten table is exactly the leak the brief wants to prevent).

## 2026-10-01 · Platform tables with a tenant column still get RLS

**Decision.** `tenant_memberships` and `tenant_addons` are read by the auth layer through the admin connection, but they carry `tenant_id` and therefore receive the same isolation policy. Uniform rule beats a special case.

## 2026-10-01 · Settings as a typed JSON blob on `tenants`

**Decision.** Operational thresholds and payment fees live in `tenants.settings` (jsonb) validated by `tenantSettingsSchema` (zod) with neutral defaults from `@hullwise/config`. Tax rates are a proper table because they are joined in revenue calculations. Adding a setting means one line in the schema and one translation key, no migration.

## 2026-10-01 · Canonical status is a stored column written by one function

**Decision.** `orders.status` is written only through `deriveOrderStatus(input, rules)` in `packages/core`. Precedence: hard facts (cancelled, voided, returned, refunded, partial return, delivered shipment) → operator-set status (`status_source = manual`) → in-transit shipment → tenant `state_rules` by priority → platform default (fulfilled → shipped, partial → fulfilling, paid → confirmed, else new). `status_reason` records which element decided, and the rules page previews the effect on the last 50 orders before saving.

**Alternatives.** Deriving the status at read time from tags (the reference platform did this in four hand-synced places and the analysis names it as the main obstacle to multi-tenancy).

## 2026-10-01 · Shipments: per-source state rows plus a resolver

**Decision.** `shipments.status` is resolved from `shipment_source_states` (one row per source: platform, carrier, aggregator, 3PL) with a per-tenant precedence and freshness window, sticky exceptions with a reason and age, and no demotion from terminal states. Today the only source is the commerce platform; a second source is a new row, not a new column.

## 2026-10-01 · Mock adapters are stateful simulators, not fixtures

**Decision.** `MockCommercePlatform` and `MockAdsPlatform` generate new orders and metrics from the tenant's own catalog on every sync, sign webhook envelopes the way Shopify does (HMAC-SHA256 base64 over the raw body), and fail on demand (`failures.failNext("rate_limited")`) so retries and health escalation can be exercised without a network. The seed writes historical data directly to the database for speed; the mocks only produce incremental activity.

## 2026-10-01 · Seed generator design

**Decision.** `generateTenantDataset(config)` is a pure, seeded function producing every row for one tenant in memory (identifiers included), then `writeDataset` bulk-inserts in chunks of 500 following foreign-key order. Full volume (15,000 + 6,000 orders, ~300,000 rows) seeds in about 40 seconds; the isolation suite reuses the same generator at 1% scale so every table is covered by construction. Timestamps are relative to the run date so the demo always has fresh orders; the random stream is fixed, so two runs on the same day are identical.

## 2026-10-01 · Money and rates as integers

**Decision.** All amounts are integer minor units (`*_minor`), rates are basis points (`rate_bps`, `returned_fraction_bps`). Formatting happens only at the edge with `Intl` using the tenant currency and the user locale.

## 2026-10-01 · A `packages/services` layer between core and the apps

**Decision.** Logic that combines the database, the pure core and the adapters (order state transitions, customer history, duplicates, notes with mentions, notifications) lives in `packages/services`, used by both `apps/web` and `packages/jobs`. `packages/core` stays free of I/O; `apps/web` keeps only request handling, authorisation and rendering. This is an addition to the fixed stack, not a change of it.

**Alternatives.** Services inside `apps/web` (rejected: jobs would duplicate them) or inside `packages/db` (rejected: it would pull adapters into the data layer).

## 2026-10-01 · Operator actions go remote-first

**Decision.** Cancelling an order calls the commerce adapter first and only then aligns the local row and recomputes the status (a webhook arriving mid-way is idempotent on the external id). Status changes and assignments are local decisions and are not written back as platform tags: Hullwise never uses tags as a state channel. Notes never leave the platform.

## 2026-10-01 · Test suites that share the test database run serially

**Decision.** `packages/db` and `packages/services` both reset and migrate `hullwise_test`. The turbo `test` task depends on `^test`, so a package's dependencies are tested first and the two suites never run at the same time.

## 2026-10-01 · Receiving is the only event that moves purchased stock and cost

**Decision.** `receivePurchaseOrder` writes an `inventory_movements` row and increments `inventory_levels` at the destination location, sets the variant's last cost and moving-average cost, moves the purchase order to `partially_received` or `received`, and recomputes backorders (`fulfilled` when stock covers them, `covered` when an open PO does). The optional Shopify write-back is a callback the action supplies, so the service stays I/O-free with respect to adapters. The reference platform wrote the product cost from the frontend on save; here cost changes only on physical receipt.

## 2026-10-01 · Inventory risk formulas and their parameters

**Decision.** `velocity = units sold in lookback / lookback days` (non-cancelled orders), `cover = (available + incoming) / velocity`, risk `critical` when effective stock is zero or cover ≤ critical days, `warning` when ≤ warning days, `no_sales` when nothing sold. Reorder suggestion `ceil(velocity × target days − effective stock)` rounded up to the variant pack size. Lookback, thresholds and target days are tenant settings; incoming counts purchase orders in `confirmed`, `in_transit` or `partially_received` (one set, used everywhere).

## 2026-10-01 · One economics function, one scope rule

**Decision.** `orderEconomics` in `packages/core` is the only place where net revenue, COGS, shipping cost, payment fee and margin are computed; dashboard, P/L, product performance and (from phase 6) campaigns call it or the SQL equivalents of its filters. "Counts as a sale" = canonical status in `confirmed, fulfilling, shipped, delivered, returned_partial`; cancelled, returned and refunded orders never count, pending ones are shown separately. Net revenue is net of tax (stored tax, or the shipping-country rate when the platform reports none) and of refunds. Missing purchase costs do not silently become zero: the P/L shows how many orders have incomplete COGS.

**Alternatives.** Counting "confirmed" orders by tag (the reference) or all placed orders (rejected: the brief wants profit only on orders that were not cancelled or returned).

## 2026-10-01 · Fixed costs prorated by day, ad spend from the ledger

**Decision.** `cost_settings` rows of kind `fixed_monthly` are prorated by days inside the period (month = 30.4375 days); `shipping_per_order` rows are matched by order date. Ad spend is the sum of `ad_metrics_daily` for the period, whatever the campaign. The hand-calculated test in `packages/core/src/finance.test.ts` and the database test in `packages/services/test/analytics.test.ts` pin the numbers.

## 2026-10-01 · Campaign profit counts only in-scope attributed orders

**Decision.** A campaign's orders are the `order_attribution` rows pointing to it (UTM campaign or click id resolved at import); of those, only orders that `orderEconomics` marks in scope (not cancelled, returned or refunded) contribute revenue, margin and count. Profit = margin − spend; ROI = profit / spend; ROAS = net revenue / spend. Ratios are never stored: the daily ledger is recomputed on every read and flags days with ads data but no orders (or the reverse) instead of showing zeros. Spend without campaign metrics in a period is still spend, so a campaign with no attribution shows a negative profit, not "no data".

**Alternatives.** Platform-reported purchases (rejected: the brief wants Hullwise's own economics, and reported conversions double count across platforms); all placed orders (rejected by the brief).

## 2026-10-01 · Recommendations are advice, pausing is explicit

**Decision.** `recommendAction` only produces a label and a reason; nothing is paused automatically. Stock wins over ROI: an active campaign whose linked products are below the tenant threshold with nothing incoming gets `pause_stock` (or `consider_stock` when a purchase order is on the way), whatever its ROI. The pause button calls the ads adapter first inside a confirmation dialog, then updates the local row and writes an audit entry; Google stays read-only in the MVP and the detail page says so instead of hiding the control silently. The stock threshold and the ROI thresholds are tenant settings.

## 2026-10-01 · Product links: one primary, auto-link only on near-certain matches

**Decision.** `campaign_product_links` allows many products per campaign with a single primary (enforced in the service, not with a partial index, to keep the seed simple). Suggestions rank URL matches from attributed landing pages above exact title matches, then prefix, contains and token overlap; the "link all" action only applies suggestions with confidence ≥ 0.95 and never overrides a manual link. Weaker suggestions are shown with their kind and confidence for a human to accept.

## 2026-10-01 · Customer profile computed from canonical orders, not from platform counters

**Decision.** Segment fields, RFM and the customer list read a profile CTE built from Hullwise's orders in sale scope (the same rule as the P/L), not from Shopify's `orders_count`/`total_spent`. The platform counters stay on the customer row as imported data. Reason: the platform counts cancelled and test orders differently per store, while Hullwise's scope is one rule everywhere. The CTE is computed on the fly (≈6k customers per demo tenant in well under a second); a materialised `customer_profiles` table is the obvious next step when a tenant passes ~100k customers.

## 2026-10-01 · One field catalog, two evaluators that must agree

**Decision.** `SEGMENT_FIELDS` in core is the only definition of what a segment field means; the SQL compiler in services maps each field to a whitelisted expression and passes every value as a bind parameter (arrays as a single parameter), so no user input is ever interpolated. The in-memory `evaluateRules` exists for tests and for the parity test that runs both against the seed. Add-ons extend the catalog through `registerSegmentFields` without touching core.

## 2026-10-01 · Holdout assignment with a dependency-free hash

**Decision.** `assignHoldout(segmentId, customerId, pct, salt)` uses FNV-1a 32-bit over `segment:customer:salt` into 10 000 buckets. The reference used Postgres `md5`; a pure function keeps core free of `node:crypto` (which would break client bundles that import core) and is identical wherever it runs. Re-evaluating a segment never moves an existing member between groups: new matches are inserted with their bucket, stale ones are deleted, the rest are untouched.

## 2026-10-01 · RFM bands and tiers are fixed in this version

**Decision.** Recency bands 0–90 / 91–180 / 181–365 / ≤ 2 years / > 2 years and frequency bands 1 / 2 / 3–4 / 5+ are constants, and the eight tiers follow the top-down rule set documented in the RFM page. Making them tenant settings is a later step; the functions already take plain numbers so nothing else changes.

## 2026-10-01 · Returns close the loop on stock and on the order, nothing else is automatic

**Decision.** The return workflow is fixed to `requested → approved → received → inspected → refunded | exchanged | voucher_issued`, with `rejected` from any open state; tenants configure reasons, window, shipping fallback and excluded product types, not the states themselves (the brief allows "configurable states within this set"; adding states would break the propagation rules). Restock is an explicit choice at `received`, per line and per location, and writes an `inventory_movements` row like a purchase receipt. Closing a return updates the order's returned fraction (goods back over goods ordered), refunded amount and payment status, and lets `recomputeOrderStatus` decide between `returned_partial`, `returned` and `refunded`: returns never set the canonical status directly. Refunds on the payment platform are not triggered from Hullwise in the MVP; the amount is recorded and the Shopify adapter can wire `refundCreate` in phase 9.

## 2026-10-01 · Discount economics use the same scope as everything else

**Decision.** A code's orders are the `order_discounts` rows whose order is in sale scope; revenue and margin come from `orderEconomics`, so a code with a negative margin shows it. Pools generate codes locally with a dependency-free generator and push them to the platform in one call; the platform's `imported`/`failed` split is stored per code (`is_active` false for failed) and the pool is marked `partial`, so a retry is a visible action rather than a silent loop. Codes synced from the platform are read-only except for enable/disable.

## 2026-10-01 · Live adapters are tested against recorded payloads, never the network

**Decision.** Every live adapter takes an injectable `fetch`; the test-suite feeds it recorded, anonymised payloads (`__fixtures__`) and asserts the normalised output, the queries sent, HMAC verification and error mapping. No test, seed or development process can reach Shopify, Meta or Google: `HULLWISE_INTEGRATION_MODE=mock` forces the simulators regardless of what the integration rows say, and the live row mode is only honoured when the env is `live`. The fixtures are the contract with the vendors; when an API version changes, the fixture changes with it.

## 2026-10-01 · One importer for webhooks, syncs and reconciliation

**Decision.** `importOrder` is the single path from a platform order to the canonical model, whatever brought the payload (webhook, delta sync, initial backfill, nightly reconciliation). It is idempotent, preserves local decisions (manual status, assignment, hold, returns), records `imported` or `platform_update` with a field diff, and hands the status to `recomputeOrderStatus`. A stale payload (older `updated_at` than what we hold) is ignored except during reconciliation. The same holds for products, customers, inventory levels and discounts.

## 2026-10-01 · Webhooks: log first, answer 200, process after the response

**Decision.** The endpoint resolves the tenant from the shop domain, verifies the HMAC with that tenant's own secret, stores the event under a unique key `(tenant, source, topic, external id, source updated_at)` and answers immediately; a duplicate delivery is a 200 with `duplicate: true`. Processing happens after the response: through pg-boss when `HULLWISE_JOBS_QUEUE=1` (a worker is deployed), inline otherwise, so a single-process demo never leaves events pending. Failed events keep their payload, are retried by the scheduler and can be replayed from the page.

**Alternatives.** Always queue (rejected: without a worker the demo stalls and tests become timing-dependent); a 60-second dedup heuristic as in the reference (rejected: the unique index is exact).

## 2026-10-01 · Resumable sync runs live in `sync_runs`

**Decision.** A sync pass is a `sync_runs` row whose cursor (`nextCursor`, `updatedSince`, `highWaterMark`, pages) is saved after every page. Delta syncs start from the last successful high-water mark minus 2 minutes; a run that exceeds its time budget is left `paused` and resumed by the next job, which re-enqueues itself. Reconciliation re-reads the last 35 days by creation date and lets equal timestamps through, so cancellations missed by webhooks are caught nightly. Health rows per source turn `degraded` on the first failure and `error` after three consecutive ones.

## 2026-10-01 · Hullwise owns the invoice ledger; the payment provider only collects

**Decision.** Subscriptions and invoices are Hullwise tables written by the console and the billing job through the admin connection. `BillingProvider` is reduced to three calls (ensure customer, create invoice, read invoice status); the mock does nothing and the Stripe implementation talks to the REST API in test mode without the SDK. Plan prices, setup fees and add-on prices come from `packages/config`, so a price change is a config change and the next invoice picks it up. Stripe webhooks and card collection are the first step after a first paying customer, not before.

**Alternatives.** Stripe Billing as the source of truth (rejected: the console must work with no Stripe account, and the demo must show the whole cycle offline).

## 2026-10-01 · Suspension is computed, manual suspension is sticky

**Decision.** A tenant is suspended when an open invoice is overdue by more than its `suspend_after_days` (default 14) and reactivated automatically when nothing overdue remains; both transitions are audited. A suspension set by hand from the console stores `manualSuspension` in the tenant settings and is never lifted by the billing job. Suspended tenants are redirected to `/suspended`; super-admins still get in for support.

## 2026-10-01 · Impersonation is implicit access made explicit in the audit log

**Decision.** A super-admin without a membership opens any tenant as `owner`; the context marks it as impersonation, the topbar shows the banner, and `auditActor(ctx)` stamps every server action with `actorType: impersonation` and `impersonatedBy`. The console's "Open as support" button also writes `impersonation.started`, so a support session has a visible beginning in the platform audit log. No separate impersonation token or cookie: there is nothing to leak or to forget to expire.

## 2026-10-01 · The COD add-on is a separate package the core never imports

**Decision.** Everything cash-on-delivery lives in `@hullwise/addon-cod` (pure logic, services and tests) plus its own tables; `apps/web` and `packages/jobs` import it behind the `addon.cod` flag, and the core packages (`core`, `services`) have no reference to it. The queue reads canonical states (`new`, `pending_review`) and writes back only through the core's manual status, so the add-on cannot invent order states. This is the guiding principle of CLAUDE.md made structural: removing the package leaves the core intact.

## 2026-10-01 · Explicit outcome machine, advice-only risk

**Decision.** Each call is an attempt with an outcome (`confirmed`, `no_answer`, `call_back`, `modified`, `cancelled`); `unreachable` arrives after N `no_answer` (tenant setting) and parks the order `on_hold` with a visible reason, instead of being inferred from tags as in the reference. The delivery score is a weighted mean of the factors that fire, listed with weight, raw value and detail so an operator can argue with it; the recipient tier only caps it. Risk profiles key on phone or email, never on names, show masked keys, and produce text suggestions (verify, suggest blacklist); nothing is cancelled or blocked automatically, and overrides require a written reason.

## 2026-10-01 · Fair-share assignment is per day and per hours

**Decision.** Operators declare hours per weekday plus day-off or extra-hours exceptions; the next order goes to the operator with the largest debt `hours/teamHours × (assigned + 1) − assigned` (smooth weighted round-robin). Every assignment, manual or automatic, is logged and counts toward the day's quota. Once an operator has registered a call, only an admin can release or transfer the order, so nobody drops a half-worked order back into the pool.

## 2026-10-01 · Demo guarantees must not depend on the clock

**Decision.** The generator is deterministic for a given `now`, but a reseed at another hour shifts the random stream and the "interesting" states (products running out, failing campaigns) could vanish. Where CLAUDE.md §10 promises something, the generator now enforces it structurally instead of relying on probability: half of the low-stock variants never get an incoming purchase order, one low-stock variant in four has zero stock everywhere and is never covered (so "critical" products always exist), and the COD seed falls back to recent recipients when no returned COD order exists. The phase-12 reseed at a different hour is what exposed the last two. Remaining probabilistic traits are documented in EVALUATION.

## 2026-10-01 · Screenshots are a script in the repo, not a one-off

**Decision.** `apps/web/scripts/screenshots.mjs` logs in as the tenant owner and as the super-admin, forces the locale through the `NEXT_LOCALE` cookie and captures every main page into `docs/screenshots/<locale>/`. Detail pages are resolved from the first UUID link of their list, so the script survives a reseed. Captures are clipped at 3200 px: a 500-row ledger is not a screenshot. The committee asked for en and it; es is one environment variable away (`LOCALES=en,it,es`).

**Alternatives.** Playwright `toHaveScreenshot` inside the e2e suite (rejected: it would turn documentation into a flaky visual-regression gate on data that changes with every seed).

## 2026-10-01 · Evaluation document names what is simulated before what works

**Decision.** `docs/EVALUATION.md` leads with the fact that no real store was ever connected and lists each mock with what it takes to make it real. The buyer must not discover this during the first installation. The ten steps start with a card-paying customer, not with the cash-on-delivery brand the reference platform was built for, because that validates the core without the add-on.

## 2026-10-01 · Platform tags are tenant vocabulary, read and written only by the add-on

**Decision.** The reference platform drove its whole COD flow through hard-coded Shopify tags. Hullwise keeps the mechanism but moves every tag into the tenant's COD settings: three read lists (queue, confirmed, cancelled; precedence cancelled > confirmed > queue, `*` suffix for prefixes) and add/remove lists per event (entered, each call outcome, unreachable, replaced). Writes go platform first through `updateOrderTags`; a refused write records nothing locally. Reads happen in the queue sync: a queue tag pulls an order in (or back in, resetting a confirmed order to review), a confirmed tag closes the item and confirms the order, a cancelled tag closes it as cancelled. Operators may be restricted to queue tags (skill routing, as the reference's `allowed_tags`). The core still never interprets a tag: outside the add-on, tags reach the status only through the tenant's state rules.

**Alternatives.** Hard-coded Italian vocabulary with overrides (rejected: it would leak one client's process into the product); a generic "tag automation" engine in the core (rejected: nobody asked for it, and the add-on is the only consumer).

## 2026-10-01 · Pre-confirmation changes: edit contact in place, replace for lines

**Decision.** Contact, address and note changes are written on the platform (`updateOrderDetails`) and locally with a diffed timeline event. Line changes and merges never use order editing: a new unpaid order is created (`createOrder`, draft order completed with payment pending on Shopify), imported through the normal importer, linked both ways (`replaces_order_id` / `replaced_by_order_id`), queued at once with the same operator; the old orders are cancelled with `cancel_reason = replaced`, tagged per settings and closed in the queue. Replaced orders are excluded from every analytics count. This copies the reference's lesson (`cancel_and_create` instead of Order Editing: a removed line stays visible to logistics and ships anyway) without copying its code. The `cancelled` call outcome now cancels the order on the platform too; before this change it only closed the queue item.

**Alternatives.** Shopify Order Editing API (rejected for the reason above); doing the replacement in two separate user actions (rejected: the operator is on the phone).

## 2026-10-01 · Per-tenant feature flags in tenant settings

**Decision.** `tenant.settings.featureFlags` is a map of named booleans read with `hasFeature(settings, key)`. It is the cheapest lever for behaviour one account wants and nobody else does, below state rules and add-ons in the escalation ladder documented in ARCHITECTURE ("Changes for one tenant"). Flags gate code paths that already exist in the product; bespoke code still goes into an `addon.*` package.

## 2026-10-01 · Period costs: estimate until the invoice, then actual, and the P/L says which

**Decision.** `period_costs` holds one row per month, kind (fixed, other, shipping) and label with an estimate and an optional actual. The P/L resolves each month as actual ?? estimate; shipping replaces the per-order estimate with the carrier invoice month by month; months with no entry fall back to the old flat `cost_settings` amount so existing tenants lose nothing. Every report carries `costSources` (actual, estimate, legacy, none, mixed) and shows it under the table: a P/L built on estimates must say so. Entry is a page under Analytics, editable by owners and admins, audited line by line. Proration changed with it: a whole month costs exactly the monthly figure (before: days/30.44, so March cost 31/30.44 of the rent); a partial month is prorated on that month's own days. The phase-5 hand calculation was updated accordingly (fixed 3043 instead of 3099).

**Alternatives.** Overwriting the estimate with the actual (rejected: the variance between the two is the information); per-day costs (rejected: invoices are monthly).

## 2026-10-01 · Blended metrics against real orders, new customers by first order

**Decision.** MER, nc-ROAS, blended CAC, POAS and CAC per paid channel are computed from Hullwise's own economics (net revenue, contribution margin, ad spend from the platforms) and from "new customers" defined as the customer's earliest non-cancelled, non-replaced order falling in the period. Platform-declared conversions are shown separately (campaigns) and never feed these ratios. Channel for CAC comes from the first order's attribution channel; spend is mapped platform → channel (Meta → paid social, Google → paid search).

## 2026-10-01 · Month-end forecast is a weekday-weighted run rate, not a model

**Decision.** The projection weights the remaining days by the weekday profile of the previous eight weeks and shows a band of one standard deviation of the daily values scaled by the square root of the remaining days. It is explainable in one sentence to a merchant, which is the point; a seasonal model belongs to the inventory forecast (Area 2), where there is enough history per SKU to justify it.

## 2026-10-01 · One touchpoint store for attribution and for the future pixel

**Decision.** `touchpoints` holds every known visit before a purchase: today the order's landing visit (from the importer) and earlier visits recorded per customer; once the Shopify Web Pixel extension is installed, every session it collects. The six attribution models are pure functions over these rows; orders without touchpoints fall back to their own attribution row, so a tenant without the pixel still gets last click and nothing breaks. "Last platform click" is modelled explicitly (the last paid click wins even if an organic visit closed the order) to show the merchant how platforms over-claim.

**Alternatives.** Computing attribution only from the landing URL (rejected: no multi-touch possible); storing sessions in a separate analytics database (rejected for the MVP: one Postgres keeps RLS and tenancy intact; partitioning by month is the path when volume demands it).

## 2026-10-01 · Seed channels use the canonical values of the importer

**Decision.** The seed used its own channel names (`meta_ads`, `google_organic`…) while the Shopify importer produces `paid_social`, `organic_search`… Everything that groups by channel (CAC per channel, LTV by channel, attribution) would have split the same traffic in two vocabularies. The seed now writes the canonical values and `CHANNELS` in core lists them.

## 2026-10-01 · Alerts: robust anomaly, not a model; delivery through sinks

**Decision.** Anomalies are the latest day against the median and median absolute deviation of the previous N days (default 28), firing at a configurable number of deviations; thresholds need N consecutive days. A cooldown stops repeats. Delivery goes through a `NotificationSink` interface: in-app always, Slack via the tenant's incoming webhook (encrypted as integration `slack`), email via the platform's provider (`HULLWISE_EMAIL_API_KEY`). In mock mode both record instead of sending and the event says `mock`, so the demo shows the whole loop offline.

## 2026-10-01 · Custom metrics are formulas over named base metrics, evaluated without JavaScript

**Decision.** A small recursive-descent parser accepts numbers, the 18 base metric names, + − × ÷ and parentheses; anything else is a validation error. Division by zero and missing values give null instead of NaN. Custom metrics are shared by the tenant; dashboards are per user. Marketing gains write access to Analytics to manage metrics and alerts.

## 2026-10-01 · Inventory forecast: seasonality per product type, level and trend per variant

**Decision.** Most variants sell a few units a month: a seasonal model per SKU would be noise. Seasonal indices are learnt on the product type over 24 months (pooled), the level is the de-seasonalised mean of the last 3 months and the trend the slope of the last 6, capped at ±8% a month. Events add their uplift in their month by scope (all, product type, product); a manual override replaces the model for that variant and month. Accuracy is the WAPE of a forecast made 3 months ago. Reorder demand is the higher of the 90-day pace and the next two months of forecast, so a coming peak raises the order before it happens.

**Alternatives.** Holt-Winters or Prophet per SKU (rejected: unstable on sparse series and not explainable to a merchant); no trend (rejected: growing products would be under-ordered).

## 2026-10-01 · Supplier confirmation by a public link, email in mock

**Decision.** Sending a PO issues a random 192-bit token stored on the PO (unique index) and marks a draft as sent. The public page `/supplier/po/[token]` resolves the tenant with the admin connection (the only cross-tenant read, by token), then works inside `withTenant`. The supplier sees agreed prices only, never landed cost or margin. Confirming moves sent → confirmed (so incoming stock covers backorders) and may change the delivery date; a problem needs a note. Both notify the PO creator and are audited as system actions. Without an email provider the link is shown to the user to forward; the provider adapter is part of the external block.

## 2026-10-01 · PDF written by a 200-line pure function

**Decision.** A purchase order PDF needs text, a table and pages. `renderPdf`/`tablePdf` in core write PDF 1.4 with the standard Helvetica fonts (WinAnsi, so € and accented letters work) and right-aligned numbers. No dependency, testable byte by byte. Non-Latin scripts are replaced with "?": when a tenant needs them, swap in a library with embedded fonts behind the same function.

## 2026-10-01 · Landed cost becomes the product cost at receipt

**Decision.** Charges on a PO are allocated to its lines by value, quantity or weight; the landed unit cost is stored per line and recomputed on every change. Receiving writes the landed cost (when present) to the variant's last cost and moving average, so the P/L margin includes duties and freight without a separate step.

## 2026-10-01 · Write permission is checked on the page, not through the "edit" action

**Decision.** `requireAction(slug, "edit", page)` checked the generic "edit" action, which belongs to the orders page: a customer-care user could change product prices. A `requireWrite(slug, page)` guard now checks the role's level on the page itself; catalog and planning actions use it.

## 2026-10-01 · XYZ on four-week buckets

**Decision.** Weekly sales per variant are mostly zeros, so the coefficient of variation put almost every variant in Z. Variability is measured on 13 four-week buckets over the last year.

## 2026-10-01 · Purchase order numbers continue from the highest of the month

**Decision.** The next number was "count of the month + 1", which collides as soon as numbers are not contiguous (imports, the seed, deleted drafts). It is now the highest numeric suffix of the month + 1, still guarded by the unique index.

## 2026-10-01 · Live mode refuses to start without the worker; Sentry errors-only, no personal data

**Decision.** `checkRuntimeConfig` (packages/config) runs when the web server (Next.js `instrumentation.ts`) and the worker start. With `HULLWISE_INTEGRATION_MODE=live` the process exits if `HULLWISE_JOBS_QUEUE` is not `1`, if a database URL is missing, or if `AUTH_SECRET` / `APP_ENCRYPTION_KEY` are missing or still the `.env.example` values; a missing `SENTRY_DSN` is a warning. In `mock` mode the same problems are warnings only, because demos and the e2e suite run the production build with the development defaults. Sentry (`@sentry/nextjs`, `@sentry/node`) is enabled only when a DSN is set, errors only (`tracesSampleRate: 0`), with one shared `SENTRY_DATA_COLLECTION` that turns off every category Sentry 11 collects by default (bodies, cookies, headers, query params, DB parameters, queue payloads, stack-frame variables): tenants' orders carry their customers' personal data. Source-map upload (`withSentryConfig`) is not wired yet: stack traces point at compiled code until it is.

**Alternatives.** Failing on `NODE_ENV=production` (rejected: it would break the e2e suite and every mock demo); keeping inline processing as a silent fallback in live mode (rejected: it is the failure mode the evaluation flagged).

## 2026-10-01 · Railway settings in the dashboard, not in `railway.json`

**Decision.** The Railway service is configured through its settings (build `pnpm install --frozen-lockfile --prod=false && pnpm build`, pre-deploy `pnpm db:deploy` — idempotent bootstrap of roles and database, migrations, and the demo seed only when `HULLWISE_SEED_ON_DEPLOY=1` — healthcheck `/api/health`, watch paths `/**`), documented in `docs/DEPLOY.md`. `next start` listens on `$PORT` (default 3000); `.node-version` pins Node 22. Empty variables copied from `.env.example` now fall back to the defaults in `db:bootstrap` and the seed (before, an empty `HULLWISE_DEMO_PASSWORD` or `HULLWISE_ADMIN_PASSWORD` became an empty password). The database handles no longer require their URL at import time: without it they return a client whose queries fail, so `next build` (which imports route modules to collect page data) needs no database variables.

**Alternatives.** `railway.json` (written first, then removed: Railway's Config as Code is deprecated, new services do not read it, and it stops being read on 2026-12-01); `.railway/railway.ts` Infrastructure as Code (deferred: it is applied with the Railway CLI or a GitHub Action with a project token, neither set up yet).

## 2026-10-01 · Return portal: public page per store, signed session, no customer account

**Decision.** The portal lives at `/r/<store slug>` and needs no login. The customer proves the order with its number and the email (or phone, when the store allows it); a successful lookup returns an HMAC-signed token valid one hour that carries tenant, order and a random nonce. Failed lookups are counted per hashed IP and per order number in `public_rate_limits` (5 in 15 minutes); the lookup returns "not found" instead of throwing so the counter is not rolled back with the transaction. Submissions carry an idempotency key. Everything the customer reads comes from `return_portal_settings` (zod schema in core): texts per language with fallback to the store language, logo, colour, offered resolutions and reasons, tracking and photo requirements, custom fields, which payment methods need an IBAN.

**Alternatives.** A customer account (rejected: friction for a one-off return); magic link by email (rejected for now: needs the email provider of the external block); order number alone (rejected: enumerable).

## 2026-10-01 · Return photos in Postgres, compressed in the browser

**Decision.** Photos are resized to 1600 px JPEG in the browser and stored as `bytea` (max 1.5 MB, 5 per request) in `return_evidence`, bound to the session nonce until submission and served to staff through an authenticated route. Railway has no object storage in the current setup, and one database keeps RLS and backups in one place. Orphans are purged nightly. Moving to an object store is a change behind the same three service functions.

## 2026-10-01 · Return write-back to the store: idempotent steps after the commit

**Decision.** A return change is committed first; `syncReturnToPlatform` then brings the store in line one step at a time (request → approve or decline → restock → refund → close → tags), saving each step as it succeeds. A failure is stored on the return (`platform_sync_status = error`, readable message) and resumed by the retry button or the job every 10 minutes without repeating completed steps. The refund goes on the original capture and is capped to what is still refundable; orders with nothing captured (paid on delivery) get a refund record without money movement. Shopify reasons are configured per return reason. The Control Room only tagged the order "RIMBORSATO"; tags per status keep that behaviour available to any store.

**Alternatives.** Writing to the store inside the transaction (rejected: a store outage would block the team and roll back their work); Shopify as the source of truth for returns (rejected: stores without Shopify returns, and portal requests must exist before the store knows them).

## 2026-10-01 · Return policy: per-line windows and blocks, staff override with a note

**Decision.** The policy (`return_policies`, schema in core) adds windows by shipping country, product type and product tag on top of the default window. When several rules match a line the longest wins, and a match replaces the default even when it is shorter (furniture to the US: 14 days). Exclusions are by product type, SKU prefix, title fragment and tag. Final sale applies from a discount threshold, on the line or against the compare-at price. A per-customer limit caps returns in a period. `orderReturnContext` computes each line's block and deadline: `returnable` is what can be returned now, `maxQuantity` what staff may still return with an override and a note. The portal never overrides. Product tags stand in for collections until collections are synced.

## 2026-10-01 · Return automations run through the normal workflow

**Decision.** Automations are evaluated in order when a return is created. Flags and fault accumulate; the first decision stops the evaluation: approve, reject, or refund without return (approve, received without restock, inspected, then refunded or voucher). Decisions call `transitionReturn` with the system as actor, so the order, the stock and the store write-back behave as if a person had clicked. Reject and refund-without-return without any condition are refused by the schema: one empty rule would otherwise reject or refund every return, which a test run proved.

## 2026-10-01 · Customer return risk is explained, never a block

**Decision.** Risk comes from the customer's history over a configurable window. It considers the return rate in items (watch and high thresholds, a minimum number of returns), customer-fault returns opened within a few days of delivery ("wear and return"), and a high returned value. It is stored on the return with its reasons, shown to the team, and usable as an automation condition. On its own it never rejects or blocks: the decision stays with the store, as for recipient risk in the COD add-on.

## 2026-10-01 · Exchanges: same-product variants, difference through a store payment link

**Decision.** An exchange line names a variant of the same product as the returned line, with the variant's current price. The return's credit is the net value of the returned units; the difference is stored on the return. When the store sync reaches an exchanged return, it creates the new order on the store. With nothing to pay, the order is created with the credit as a fixed discount and imported, and a negative difference is refunded when the policy says so. With something to pay, a draft order is created and its invoice sent; the order is linked back to the return when it arrives, through the `hullwise_return_id` attribute read by the importer. Exchanging for a different product is left out: store credit with a bonus covers "shop later" without a public catalogue in the portal.

## 2026-10-01 · Vouchers are created on the store

**Decision.** Before, an issued voucher was a code that existed only in Hullwise. The store sync now creates it as a one-use fixed-amount discount code for the credit, bonus included. The credit bonus applies to the accepted value; an amount typed by hand gets no bonus.

## 2026-10-01 · Instant exchange behind a payment-guarantee interface

**Decision.** With instant exchange on, an approved exchange gets a hold of the returned items' value through `PaymentGuarantee`, and the replacement ships immediately. The hold is voided when the goods arrive and captured by the returns job after the configured days, with the return flagged for review. A failed hold flags the return and ships nothing early. Only the mock exists: a live hold needs Stripe manual capture or Shopify Payments vaulted cards, which is part of the external block.

## 2026-10-01 · Return costs are a contribution line, from settings

**Decision.** Each return whose goods come back costs a label and some handling. Both are tenant settings, zero by default. The P/L adds "return costs" for the returns received in the period, minus the return shipping charged to customers at fault. It sits inside the contribution margin, as a variable cost, next to shipping and payment fees. Returns refunded without the goods coming back cost neither. With the settings at zero, every existing figure is unchanged.

## 2026-10-01 · Customer tracking page and return labels reuse the portal access

**Decision.** The tracking page lives at `/r/<store>/track` and uses the same lookup, rate limit and branding as the return portal. It shows the canonical order status, parcels, carrier events and returns, and never prices or internal notes. Return labels come from a `ReturnLabelProvider` at submission; the tracking code replaces any code the customer typed. Hullwise renders the label PDF on demand behind an HMAC-signed link, so nothing is stored. Only the mock provider exists until a carrier account is connected.

## 2026-10-01 · Landing page as a separate static app (`apps/landing`)

**Decision.** The marketing site is a second Next.js app in the monorepo with `output: "export"`: plain HTML, CSS and pre-optimised WebP, deployable on Vercel with root directory `apps/landing` or on any static host. It shares the workspace (`@hullwise/config` for `PRODUCT_NAME`, the ESLint config, Tailwind 4, next-intl) but not `@hullwise/ui`: the design tokens are copied into `apps/landing/src/app/globals.css` so the landing has a marketing look (large serif headings, generous spacing, browser-frame screenshots) rather than the dashboard chrome, and so the app deploys without the Radix dependency tree.

**Alternatives.** A route inside `apps/web` (rejected: the product is server-rendered behind auth and a database; the landing must build and deploy without either). Importing `@hullwise/ui/styles.css` (rejected: pulls the component scan and base styles meant for the dashboard).

Cookie-based locale like the product (rejected: a static site has no request to read a cookie from, and SEO needs one URL per language). Locale prefix for English too (`/en/`) (rejected: the default language at the root is the usual convention and keeps `x-default` trivial).

## 2026-10-01 · Pricing numbers in one file, pricing words in the message files

**Decision.** `apps/landing/src/config/pricing.ts` holds every number, threshold and flag (plans, overage, annual months charged, add-ons, founding offer, stack comparison figures). Translated copy for plans, features, add-ons and FAQ lives in `messages/<locale>.json` keyed by the identifiers in the config. The founding discount applies to monthly billing only; the annual toggle shows list prices with two months free, so the two offers never stack and both stay explainable in one sentence.

Stacking the founding discount with the annual discount (rejected: 50% off year one is a pricing decision the brief did not take; stacking is one line to enable if wanted).

## 2026-10-01 · Customer predictions with MBG/NBD and Gamma-Gamma, fitted per tenant

**Decision.** `packages/core/src/predictions.ts` fits two textbook "buy till you die" models by maximum likelihood (Nelder–Mead in log space, no dependency): MBG/NBD for purchase rate and drop-out, Gamma-Gamma for order value. Per customer it gives P(active), expected orders at 90 and 365 days, expected order value, predicted value over 12 months and an expected next-order date: last order plus the customer's own average gap, or the store's median gap to the second order for one-time buyers; none when the risk is high. Purchases on the same calendar day count once. Only sale-scope orders count, as in the profile and the P/L. The fit needs at least 50 customers; below that the tenant gets an "insufficient data" model row and no predictions. `a` is kept above 1 so the expected-purchases formula is defined. Every run back-tests itself: fit on orders up to 180 days ago, predict the following 180 days, compare with what happened. The page shows the result next to the predictions.

**Alternatives.** BG/NBD (rejected: a one-time buyer can never drop out, so P(active) stays 1 for most customers of a typical store). Pareto/NBD (rejected: same quality, harder numerics). A gradient-boosted classifier on RFM features (rejected: needs labelled history per store, is harder to explain, and needs a training pipeline; this model fits in under a second per tenant and has published, checkable formulas). Recency thresholds only (rejected: ignores each customer's own rhythm).

## 2026-10-01 · Churn risk is P(active) in three bands, thresholds per tenant

**Decision.** Churn risk is low when P(active) is at least 70%, medium from 40%, high below. Both thresholds are tenant settings (`churnLowPct`, `churnMediumPct`); medium is clamped to never exceed low. Predictions are recomputed nightly at 03:40 UTC, after the reconciliation, and on demand by anyone who can edit segments. The stored rows are replaced on every run, so a customer whose orders are cancelled loses the prediction.

**Alternatives.** Relative bands by percentile (rejected: "high risk" would exist even in a store where everyone is active). Probability of no purchase in the next 90 days (rejected: it marks every slow but loyal customer as at risk).

## 2026-10-01 · Demo customers follow a lifecycle

**Decision.** The seed generator used to pick each order's customer by a skewed index with no notion of time, so no customer ever stopped buying. Fitted on that data, the prediction model put 94% of customers at low risk. `lifecycleCustomerSequence` now simulates each customer: acquisition (a third before the data window), a personal purchase rate (Gamma), and a drop-out chance after each purchase (Beta, mean 26%). It then maps the event sequence by rank onto the seasonal order dates the generator already samples, so volume, seasonality and growth are unchanged. On the demo the back-test error is 0.8% (Northwind) and −12.5% (Harbor, partly the generator's growth trend), and churn risk spreads across all three bands. The isolation suite now seeds at 3% instead of 1%, so both demo tenants have the 50 customers the model needs; it still runs in about 8 seconds.

**Alternatives.** Retrying a pick until it lands on an active customer (tried: surviving customers then buy faster as others lapse, and the back-test under-predicted by 27%). Lowering the model's customer minimum so the 1% test seed fits (rejected: a product limit should not bend to a test fixture).

## 2026-10-01 · The customer profile CTE is materialized

**Decision.** Every query over the customer profile (`with p as materialized (...)` in `packages/services/src/crm/index.ts`) now computes the per-customer aggregates once. Without the hint, Postgres inlined the CTE and misestimated the RFM `case` filters. It then re-ran the order aggregations inside a nested loop: the segment preview's sample query took 4.4 s on Northwind and now takes 0.24 s.

**Alternatives.** A materialized view of profiles refreshed by a job (rejected for now: the profile must reflect orders immediately, and the hint fixes the measured cost).

## 2026-10-01 · Customer campaigns use the segment's control group and intention-to-treat results

**Decision.**
- A customer campaign targets one segment, and its control group is the segment's holdout. That assignment is the one the data model already keeps stable per customer, so a customer held out of a segment is never messaged by any campaign on it.
- Consent is applied before the split is read: only customers who accept marketing enter either group, so the groups stay comparable.
- Results are intention-to-treat. Every treated customer counts, including those whose message failed or who had no address. The outcome is sale-scope orders in the attribution window after exposure, with the P/L's per-order economics.
- Incremental margin is (treated − control) margin per customer × treated customers, with a Welch 95% interval. Uplift significance is the two-proportion test already in core. Before sending, the dialog shows the minimum detectable effect, so a control group too small to say anything is visible.
- Sending is synchronous through `MessagingChannel` (mock).
- The "manual" channel records exposures for campaigns sent from another tool.

**Alternatives.**
- A fresh random split per campaign (rejected: it ignores the stable holdout the brief put in the data model, and customers would drift in and out of control groups).
- Per-protocol results that count only delivered messages (rejected: deliverability differs between customers, so the comparison would no longer be randomised).
- Queue-based sending (deferred: needed with real providers and large audiences, which is the external block, issue #7).

## 2026-10-01 · Seeded campaign effect comes from real orders

**Decision.** For the demo's measured win-back campaign, about 12% of the treated customers get one extra order within the window. Each one is a copy of the customer's own last delivered order (lines included, generated columns recomputed) and uses the campaign code. The P/L, the customer history and the campaign results therefore all see the same orders, and the effect on the page is computed, not typed in. Harbor's campaign has no injected effect, so the demo shows a "no clear effect" verdict too. The seeded repeat-customer segments now hold out 20% instead of 10%. With 10% the control group had about 150 customers, a standard error of about 2.6 points, and the seeded effect was not significant on one reseed in two.

**Alternatives.** Hard-coding result numbers (rejected: the results page would disagree with the orders it links to). Raising purchase rates inside the lifecycle generator (rejected: segment membership is only known after the orders exist).

## 2026-10-01 · Control groups and customer campaigns are an add-on (`addon.customer_campaigns`)

**Decision.** The client's ruling is that treated and control groups only matter to a store that sends campaigns through WhatsApp or email. Campaigns, the holdout setting, group badges and uplift measurement are now the add-on `addon.customer_campaigns` (page key `customer_campaigns`, 99 USD a month as a placeholder price).

Without the add-on:
- the segment builder has no holdout field, and the server forces 0% on save;
- lists, member tables and the customer page show no groups;
- the CSV export has no group column;
- audience destinations include every consenting member;
- the campaign pages and actions return 404 or are forbidden, server side included.

The `holdout_percentage` and `group_name` columns stay in the data model, as §7.3 of the brief asks. If the add-on is switched off later, existing groups are kept but ignored. Spoki and other WhatsApp providers become channels of this add-on. The landing does not list it yet.

**Alternatives.** Keeping control groups in the core with an "advanced" toggle (rejected: the client decided). Dropping the columns (rejected: the brief keeps them in the data model, and the add-on needs them).

## 2026-10-01 · Live segments: incremental every 10 minutes, full every night

**Decision.**
- A segment marked live is re-checked every 10 minutes (job `segments`) for the customers whose orders or profile changed since its last evaluation. The profile query is restricted to those customers in every branch, so the cost does not depend on the store's size.
- Each night after the predictions (job `crm`), live segments are fully re-evaluated, because conditions on elapsed time and predicted values change without any event.
- The incremental and full results agree; the service test checks it. Existing members never change group.

**Alternatives.** Re-evaluating on every webhook inside the order transaction (rejected: it couples order ingestion to every segment rule, and a ten-minute delay is fine for audiences). Database triggers (rejected: the segment rules compile in the service, not in SQL functions).

## 2026-10-01 · Reliable platform writes and sync: outbox, idempotency, reconcile runs, stock drift, retention (issue #24)

**Decision.**
- **Outbox.** Every write to Shopify, Meta or Google is a row in `platform_writes` (tenant table, RLS). The user action writes the local change, the audit entry and the outbox row in one transaction, then the write runs. With a worker (`HULLWISE_JOBS_QUEUE=1`) it goes through the pg-boss queue `platform.write`. Without one it runs inline right after the commit, so the single-process demo behaves the same.
- **Local first.** For asynchronous writes the local change is applied at once and the platform follows; a failure shows as "Sync failed" with the platform's error and a Retry button on the record and on the Integrations page. The nightly sync re-aligns Hullwise with the platform's truth for anything that never lands. This replaces "platform first" in price, product status, order cancellation, single discount codes, stock pushes (purchase-order receipt, transfers) and Meta pause/resume.
- **Retries.** Rate limits, network and unknown errors are retried: the first wait is the platform's Retry-After, then 30 s × 2^n, at most 1 hour, up to 6 attempts. Permission, invalid-request, not-found and unsupported errors fail at once. A `writes` tick runs every minute: it puts writes left `running` by a restart back to pending, executes due rows oldest first, and stops a tenant's batch for a provider on a rate limit. The pg-boss job never throws for a platform error: the outbox owns the retry policy.
- **Idempotency.** Without a caller key the key is a hash of kind, target, payload hash and the id of the previous write on the same target. The same request within 10 minutes (double click, repeated action) returns the same row, even concurrently: the unique index on (tenant, key) makes the loser read the winner's row. A → B → A gives three writes, because the previous write is part of the key. Kinds that write absolute values (price, status, stock level, campaign status) supersede older pending or failed writes on the same target, so a late retry can never overwrite a newer value.
- **Synchronous writes stay synchronous, recorded.** `runPlatformWriteNow` runs the same registered handler with an adapter the caller holds and records the call and its outcome (`mode = sync`). It is used where the flow needs the answer:
  - COD tags and the COD cancellation: the add-on's contract is "a refused write changes nothing locally", and its tests assert it;
  - COD contact edits and the replacement order, whose number and lines are imported immediately;
  - the return write-back steps, already a resumable per-step machine, now keyed `return:<id>:<step>`;
  - discount pools, where the form reports accepted and rejected codes.

  With a key, a repeated call returns the stored result (the replacement order is revived with its dates); without one each call is its own record. A synchronous record rolls back with the caller's transaction, and the error is shown to the user at once.
- **Google** campaign status changes are refused before anything changes (read-only in the MVP), instead of failing in the outbox.
- **Reconcile runs.** `sync_runs` gains `rows_scanned`, `conflicts`, `error_count`, `duration_ms` and `summary`. Conflicts count platform values that disagree with Hullwise: stock drift, and objects with a Hullwise write not yet confirmed. The catalog run is resumable by phase (locations → products → stock → discounts → cleanup) with cursors saved after every page. The nightly run is `kind = reconcile` and is shown on the health page with its summary.
- **Stock.**
  - `inventory_levels.synced_at` now means "when Hullwise last read this level", not the platform's update time.
  - A complete run sets to zero the levels of active variants it did not see, and logs them.
  - Negative platform values are stored as zero and logged.
  - A level with an unconfirmed `inventory.set` write is not overwritten.
  - Drift is "the change since the last read minus what Hullwise can explain". The explanation is the variant's sales since then, minus cancellations since then of earlier orders. Sales carry no location, so the check is per variant, and receipts and transfers are already in the local level. Drift rows are deduplicated on a key, and a repeat bumps `occurrences`.
- **Webhook stock refresh.** After `orders/*`, `fulfillments/*` and `refunds/create` (now registered), the stock of the order's variants is re-read in the same job, in a savepoint. A failure is recorded on `shopify:inventory` health and never fails the webhook; the nightly run catches up. A separate queue job was rejected: it would need plumbing in three call sites (job, inline route, replay) for no gain at this volume.
- **Mock coherence.** The commerce mock now keeps stock per item and location, seeded from the tenant's levels. Orders it generates take stock from the default location, restocked cancellations put it back, and `setInventory`/`restockInventory` change it. A sync therefore shows only real changes; `adjustStock` simulates an edit in the store admin.
- **Retention.** The window is platform-wide: `HULLWISE_RETENTION_DAYS`, default 14 (`PLATFORM_RETENTION_DAYS_DEFAULT`). A daily tick at 04:10 deletes, per tenant through `withTenant`:
  - processed webhook events;
  - succeeded or superseded writes, and synchronous records (their flow owns the failure);
  - successful runs, and failed runs already followed by a success;
  - drift not seen since.

  Failed webhooks and failed asynchronous writes are kept until resolved. pg-boss queues get the same window as `deleteAfterSeconds`.

**Alternatives.**
- Keeping "platform first" with an in-request retry: rejected, because a rate limit or timeout would still lose the write or block the user.
- A generic per-request dedupe table: rejected; the key on the outbox row is enough and keeps the status on the record.
- Time-bucketed keys: rejected; a double click across a bucket boundary would write twice, and A → B → A would collide.
- Clamping negative stock at the platform: rejected; Hullwise never writes stock it did not decide.

## 2026-10-01 · Lists: bulk actions, saved views, ⌘K search, CSV export (issue #25)

**Decision.**
- Bulk actions call services, never adapters: `bulkOrders`, `bulkProducts`, `bulkReturns` (packages/services/src/lists/bulk.ts) run each record in its own tenant transaction through the same write as a single record (platform first, then the local row and the timeline event), at most `BULK_CONCURRENCY` = 3 at a time, through the generic `runBatch` runner. Every record ends as done, skipped with a reason code (`already_cancelled`, `bad_transition:<status>`, `unchanged`, …) or failed with the error; one failure never stops the others. One `batch_id` goes into every per-record audit row and every `OrderEvent` metadata, and a closing `bulk.<entity>.<action>` audit row stores the counts and the failures. Selection is the rows shown on the page (at most `BULK_MAX_ITEMS` = 200 per call); "select all matching the filters" is not offered.
- Platform writes of bulk actions go through new service functions (`orders/writes.ts`, `catalog/writes.ts`); single-record actions keep their current code for now. When the write queue of #24 lands, these functions are the one place to route through it.
- Return transitions in bulk use `transitionReturn`; the platform write-back runs after each record's commit as for one return and never turns a done record into a failure (its error is shown as the record's note and stays on the return for the retry button). Refund in bulk refunds the inspected amount; returns not yet inspected are skipped with the reason.
- Products: bulk price (set an amount or move by a percentage, rounded, never negative) and compare-at (set or remove) apply to every variant of the selected products. `CommercePlatform.updateVariant` takes `compareAtMinor` (null removes it) and a new `updateProductTags`.
- Permissions per bulk action live in `BULK_ACTIONS` (packages/config/src/lists.ts): a named action of the matrix (`cancel_order`, `change_order_state`, `assign`, `approve_return`) or write level on the page. The selection column is rendered only when the role has at least one action.
- Saved views: table `saved_views` (tenant, page key, name, canonical query string without the page number, owner, shared flag). Private views are visible to their owner, shared views to everyone who can open the page; saving with a name the user already used on that list replaces it. Owners and admins may delete others' shared views. Every create, update and delete is audited.
- ⌘K: one server action, one tenant transaction, at most four small queries (5 rows each), only for the areas the role can open. Order numbers with or without the tenant prefix, emails (normalized), phones (normalized to E.164 with the tenant's country, so the international and the local format find the same rows) and text through the existing trigram index on `orders.search_blob`; new trigram indexes on product title, variant SKU and the customer name/email expression.
- Filters of the orders, products, customers and returns lists moved to `packages/services/src/lists/filters.ts` (`parse*Filters`, `orderListWhere`, `productListWhere`), so the page, the CSV export and the background job read the same query string the same way. `?product=` and `?variant=` on Orders (orders with at least one line of that product or variant) are linked from the product page (header and each variant) and from product performance in Analytics (with the period).
- CSV: `GET /t/<slug>/<list>/export?<filters>` for orders, products, customers and returns, same filters as the page, UTF-8 with BOM, cells that a spreadsheet would run as formulas prefixed with an apostrophe. Up to 5,000 rows the file is returned at once; above that a `list_exports` row is queued (`list.export` job, or run after the response when no worker is deployed), the user lands on `/exports` and gets an `export_ready` notification. Files are stored in the table and only their owner can download them; request and download are audited. Export needs the page and either write level or the `export` action. Purchase orders and analytics tables have their CSV from their own work; the purchasing page gets saved views only.

**Alternatives.**
- One transaction for the whole batch (rejected: one failure would roll back the records already written on the platform). Running the bulk action as a background job with progress (deferred: 200 records at concurrency 3 finish within a request; the queue of #24 will carry retries).
- Saved views in browser storage (rejected: CLAUDE.md §12, and views must be shareable). Views keyed by full URL (rejected: the canonical query keeps "same filters, different order of keys" one view).
- A search index table or an external search service for ⌘K (rejected for the MVP: indexed per-area queries on the tenant's rows answer in milliseconds on the demo volumes).
- Streaming large CSVs straight from the request (rejected: long requests time out on the host; a stored file plus a notification also survives the user closing the tab). Object storage for export files (deferred: text in Postgres is enough at the 100,000-row cap; purge with the retention work).

## 2026-10-01 · Analytics depth: P/L per order, P/L over time, products with ads and stock, UTM drill-down (#31)

**Decision.**
- **One source of truth.** Every new view reuses `orderEconomicsForPeriod` / `orderEconomics`; `pnlForPeriod` was split so `pnlFromRows` builds the period P/L from rows already loaded (no second pass). The order page card shows exactly `orderEconomics` for the order plus its own return costs (`orderPnl` in core): contribution = order margin − return costs.
- **Per-order table reconciles by construction.** Net revenue, tax, cost of goods and payment fees of the rows add up to the period P/L. Two items exist only at period level and are shown as their own reconciliation lines instead of being spread on orders: the carrier invoice minus the per-order shipping estimates (months with an actual invoice), and return costs by receipt date (the P/L) minus return costs of the period's orders (the table). Then ads and fixed costs lead to operating profit. `reconcileOrderPnl` in core; the page shows a check mark when the walk equals the P/L.
- **Buckets.** Day / week (ISO, Monday) / month / quarter / year in UTC, like period costs, ad spend days and the orders list date filter. A bucket is `partial` when the selected period cuts it or it is still running. Order amounts go to the order's bucket, ad spend to its day, return costs to the receipt; shipping is allocated month by month in proportion to the per-order estimates (time when the month has no order), fixed costs in proportion to time. `allocateMinor` (largest remainder) makes every allocation exact, so buckets add up to the period P/L to the cent (tested in core and on the seed for all five granularities). Default granularity follows the period length; `gran` in the URL overrides it.
- **Product ad spend.** A campaign's spend goes to the products linked to it (`campaign_product_links`), split by the products' net revenue in the period (evenly when none sold). Campaigns without a linked product go to an "unattributed spend" row, so product spend + unattributed = period ad spend, with the same day bounds as the P/L. Product net revenue is the line total after line discounts × (order net revenue / order gross), i.e. tax and refunds removed pro rata like the P/L; cost of goods is reduced by the returned fraction like `orderEconomics`. Profit = net revenue − cost of goods − ad spend; ROAS/ROI and the campaign traffic light (ROI thresholds of the tenant) only for products with spend.
- **Stock action** (`productStockAction`, core): pause ads when nothing is left to sell; reorder (with the suggested units) when the worst variant is at risk and the product can be bought again; last units / pause ads for one-off products; clear excess when cover exceeds `excessCoverDays` or the product has stock and no recent sales; scale ads when ROI is good and stock is healthy. The worst variant decides the risk, as on campaigns. On the demo seed most products show "clear excess" because stock is high compared with sales: the data, not the rule.
- **UTM drill-down** reads `order_attribution` (UTM fields as stored at import): values compared trimmed and case-insensitive, empty = `(none)`; click order source → medium → campaign → content → term, parents kept as URL params. Channel trend: net revenue per attribution channel per bucket, top 5 channels plus "other". The orders list gained the matching filters (`utmSource`…`utmTerm`, `attrChannel`, `product`) with removable chips, using the same normalisation, so every number opens the orders behind it.
- **Payment fee** stays the tenant's estimate per method and is labelled "estimated" (`paymentFeeSource: "estimated"` on `OrderPnlDetail`), so the payments work (#27) can switch it per order.
- **Tables** are paginated server-side with URL state (filters by GET forms, no client state); totals cover every filtered row, not only the page. CSV through `GET /t/[tenant]/analytics/export/{orders|products|utm|pnl}` with the page's guards, period and filters. Charts are Recharts with colours from CSS variables (`--color-chart-N` with fallbacks to existing tokens), one money axis, no hard-coded hex.
- The economics card is shown only to roles that can read the analytics page (customer care does not see margins).

**Alternatives.** Allocating period-level shipping and return costs to orders (rejected: invents per-order numbers nobody can check; the reconciliation lines say where the difference comes from). Bucketing in the tenant time zone (rejected for now: period costs, ad spend days and order list filters are UTC; moving all of them together is a separate change). Splitting campaign spend by attributed orders' lines (rejected: attribution covers a minority of orders and would leave most spend unattributed; the link table is what the campaigns page uses for stock advice). A per-product spend share from campaign names (rejected: links already carry the suggestions).
## 2026-10-01 · Purchasing depth (#29): default supplier, PO editing, case packs, inspection, supplier links

**Decision.**

Keeping plain tokens with an expiry column (rejected: a leaked database would expose live links).

  - contact and address edits use `order.update_details`;
  - the replacement order uses `order.create`, keyed `order:replace:<order ids>`, so a repeated request reuses the order already created;

## 2026-10-01 · Fulfilment and shipping operations (#28): late-to-ship queue, ship from Hullwise, exception queue, return-to-sender review, status mappings

**Decision.**
- **"Paid, unfulfilled" is "ready to ship".** The queue takes orders in the canonical statuses `confirmed` / `fulfilling` (decided by the tenant's state rules), with no shipment and not fulfilled on the platform. It does not read the payment method or status: a prepaid order and an order whose rules confirm it without payment are treated the same, so the core stays payment-method agnostic. The clock starts at `placed_at` (there is no reliable "paid at" across methods).
- **Working days.** New tenant settings `lateToShipBusinessDays` (default 2) and `workdays` (ISO weekdays, default Monday–Friday), counted on local dates of the tenant time zone: an order is 0 on the day it was placed and late when more than the threshold working days have passed. `lateToShipCutoff` converts the threshold into one instant (start of the (threshold+1)-th most recent working day), so SQL filters with one comparison; a property test checks cutoff and count agree. No holiday calendar yet (a list of dates can be added to the same setting). `lateToShipHours` stays in the schema for old rows and is no longer read. The existing `checkLateToShip` (#33) now uses this count; the notification body is the threshold in working days.
- **Alert rule when above N** is the existing alert-rule engine with a new snapshot metric `late_to_ship` (like `stockouts`); the seed adds one rule per tenant.
- **Pick/pack** is two nullable columns on `orders` (`packed_at`, `packed_by`), not a new table: one stage per order, shipped = it has a shipment. Bulk "mark packed" uses `runBatch` (per-order transaction, outcome per order, `batch_id`); bulk packing slips are one PDF built with the existing core PDF writer (`tablePages` / `tablesPdf` extracted from `tablePdf`).
- **Ship** adds `CommercePlatform.createFulfillment` (Shopify: open fulfillment orders → `fulfillmentCreate` with tracking info; scope `write_merchant_managed_fulfillment_orders` added to `core.shipments`; mock fulfils its simulated orders and acknowledges unknown ones) and the write kind `fulfillment.create`, executed with `runPlatformWriteNow` keyed `order:<id>:fulfil:<tracking>`. Hullwise imports the shipment from the platform's answer with the same `importFulfillment` the sync uses, so a later webhook updates the same row. Shipping clears a manual pre-shipping status (confirmed, pending review…) because shipping is a fact past it; `on_hold` orders are not on the board. One fulfilment per order (all remaining lines); partial shipments from the board are not in scope.
- **Cases** live in one table `shipment_cases` with `kind` (`exception` | `return_to_sender`), a partial unique index (one open case per shipment and kind) and the claim, instruction and follow-up columns. Cases open from the resolved status on import and in the hourly `notify` sweep, only for changes in the last 30 days (`DELIVERY_CASE_WINDOW_DAYS`) so the seed history and a first sync do not flood the queue. A closed review is never reopened; a closed exception reopens only if the shipment falls into exception again after the closure. An exception case closes by itself when the visible status leaves the exception (the resolver's sticky-exception rule still applies: back "in transit" within the sticky window does not count as moving on).
- **Claim exclusivity and send-once** are conditional updates (`claimed_by is null`, `instruction_sent_at is null and claimed_by = actor`) inside the request transaction, before any external call: concurrent requests serialize on the row lock and the loser sees the row already taken. A failed carrier call or email rolls the transaction back, so the case can be sent again. Owners and admins can release a colleague's case. Only the claimer acts on a case; follow-ups on a review claim it on the way.
- **Instruction channel.** `CarrierProvider.sendInstruction` (mock only; available in mock mode, none in live mode until a carrier connector is sold) or the new `carrier_instruction` transactional email template to the carrier's customer-service address (`carrierInstructionEmail` setting, editable per send). No vendor connector.
- **Return-to-sender follow-ups** are suggestions computed in core (`suggestRtsFollowUps`): restock (until a restocked return exists), refund only when money was captured and not refunded, contact when the order has an email or phone. They are marked done/skipped by a person; restock links to the return flow, refund to the order. Cancelling and voiding uncaptured payments is out of scope here (add-on issue).
- **Status mappings.** The resolver reads `shipment_status_mappings` on every fulfilment import: matched case-insensitively on (source, external status), it sets the canonical status, an exception flag (a non-exception status becomes `exception`) and a final flag (beats non-final sources). The source state row stores the mapped status and the raw external status. Settings → Fulfilment edits the table (audited, one row per source and status) and lists external statuses seen but not mapped.
- **Permissions.** The fulfilment pages use the `shipments` page level (operations, owner, admin write; customer care and viewers read); settings need `manage_settings`.

**Alternatives.** A separate pick/pack table (rejected: one stage per order, two columns are enough). Two case tables (rejected: same lifecycle and queue UI). Counting hours instead of working days (rejected by the issue). An outbox kind for carrier instructions (rejected: the outbox is for commerce and ads platforms; the case row is the record and the guard). Reading the payment status in the queue (rejected: it would push one payment flow into the core).
## 2026-10-01 · Platform transactional email with Resend (#51): provider, templates, queue, suppression, delivery log

**Starting point.** #33 had merged an email layer: `notifications/mailer.ts` (`sendTenantEmail`, `sendPlatformEmail`, `platformMockEmails`, signed unsubscribe links, per-tenant `email_suppressions`), `notifications/email-templates.ts` (`renderEmail`, strings in code), the `HttpEmailSink` (Resend-shaped HTTP) used by alerts, notifications and the email change, `getPlatformEmailSink` with a printing mock, a bounce webhook authenticated by `?token=` (`HULLWISE_EMAIL_WEBHOOK_SECRET`), and the magic link going to `MAGIC_LINK_WEBHOOK_URL` or the platform sink. Every send happened inside the request or the job that triggered it, with no log.

**Decision.** One email code path, evolved from that layer:
- **Adapter** (`packages/integrations/src/email`): `EmailProvider.send({ from, to, subject, html, text, replyTo, tags, headers, idempotencyKey }) → { id }`; `ResendEmailProvider` over HTTP with the `Idempotency-Key` header, a 10 s timeout, no internal retries (the queue owns them) and error mapping to `rate_limit | invalid_recipient | domain_not_verified | auth | invalid_request | transient | timeout` with `retryable`; `MockEmailProvider` records messages, keeps one copy per idempotency key like Resend, and can fail on demand. Svix signature verification (`verifySvixSignature`) and `parseResendEvent` live next to it. Tests use recorded payloads through an injected fetch. `emailAddressHash` (HMAC-SHA256 keyed with `APP_ENCRYPTION_KEY`) and `maskEmail` are in `crypto.ts`.
- **Provider selection** (`emailSettings`): Resend only when `RESEND_API_KEY` is set AND `HULLWISE_INTEGRATION_MODE=live`; otherwise the process-wide mock (`mockEmailOutbox`, on `globalThis` so every Next bundle shares it). States `configured | not_configured | mock_mode`; the console shows "Email not configured" and `checkRuntimeConfig` warns in live mode (missing key, missing `EMAIL_FROM`, missing `RESEND_WEBHOOK_SECRET`). Variables: `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO`, `RESEND_WEBHOOK_SECRET`, optional `EMAIL_LEGAL_NAME`, `EMAIL_LEGAL_ADDRESS`, `EMAIL_SUPPORT_ADDRESS` for the footer.
- **Templates** moved to `packages/services/src/email/templates.ts`; strings moved out of code into `email/messages/{en,it,es}.json` (a test keeps the keys identical). Typed props per template; registry `EMAIL_TEMPLATES` with kind (`security | transactional | notification`) and default suppression category. New templates: `email_change_confirm`, `email_change_notice`, `test`. Layout: product mark (initial of `PRODUCT_NAME` on a primary square, no image so it renders with images blocked), product name, footer with reason, support address and legal sender; colours from direction A (`@hullwise/ui/tokens`, imported by services for this only) with a `prefers-color-scheme: dark` override and `color-scheme` meta. A snapshot test covers HTML and text of every template in every language.
- **Queue** (`email/mailer.ts`): `queueEmail(ctx | { db }, { to, template, data, locale, event, category?, expiresAt? })` renders, checks both suppression lists, inserts the log row with `idempotency_key = sha256(tenant|template|recipient|event)` (unique; a second call returns `duplicate`) and hands `{ messageId, payload }` (rendered message, AES-GCM encrypted because it carries links) to the dispatcher. Dispatchers: the worker sends a pg-boss `email.send` job (2 s delay so the queueing transaction commits); the web process enqueues the same job when `HULLWISE_JOBS_QUEUE=1`, otherwise delivers in process after the response (instrumentation installs it); with no dispatcher (tests, scripts) jobs wait in memory for `drainEmailJobs`. `deliverEmailJob` claims the row (`queued → sending`, stale claims after 2 min), re-checks suppression, sends with the row's idempotency key, and on a retryable error requeues with backoff 30 s / 2 min / 10 min / 30 min up to 5 attempts (a provider `Retry-After` wins); security emails become `expired`, never sent, once `expires_at` passes or the next attempt would land after it. A row not visible yet returns `missing` and pg-boss retries; a rolled-back email never goes out.
- **Delivery log** `email_messages` (nullable `tenant_id`, RLS like `audit_logs`: a tenant reads and appends only its rows; the sender and the console use the admin connection): template, category, kind, recipient hash + masked form, locale, status (`queued | sending | sent | delivered | delivery_delayed | bounced | complained | failed | suppressed | expired`), provider and provider id, attempts, last error code and text (sanitized: links, addresses and long tokens are replaced). Never the body, the props or the links (test). Retention: final rows after max(window, 30 days); `emails` tick every 10 min retries provider events and closes queued rows whose in-process job was lost (after a day).
- **Webhooks** `/api/webhooks/email`: Svix headers verified with `RESEND_WEBHOOK_SECRET` (503 without it, 401 on a bad signature), event stored in the platform table `email_events` (unique on provider + event id, recipients as hashes, only the `template`, `message_id`, `tenant_id` tags), 200 at once, processed by pg-boss `email.event` or inline after the response. Status only moves forward (a late "delayed" never undoes "delivered").
- **Suppression**: provider hard bounces and complaints go to the platform table `email_address_suppressions` (hash + masked, unique per reason), since the sender is one for every tenant; a bounce blocks every email, a complaint every email except security ones; soft bounces only note the error. Per-tenant `email_suppressions` keeps unsubscribes and manual entries (category rules unchanged; security emails ignore unsubscribes and complaints, never bounces). Campaigns (#34) can reuse both through `isAddressSuppressed` / `suppressedAmong`.
- **Moved onto the queue**: notification emails (`notifyUsers`, event = the notification row id, now generated before the insert), mentions, digests (event = user + day, so a second run of the tick the same day is a no-op), supplier PO emails, invitations, alert emails (the notification template per recipient, event = rule + firing time; the alert event records `email: queued`), the email change (security templates replacing the web-side strings and the platform sink), the magic link (security template, expiry from Auth.js, console print only in development with the mock).
- **Removed**: `sendTenantEmail`, `sendPlatformEmail`, `platformMockEmails`, `getPlatformEmailSink`, `ConsoleEmailSink`, `HttpEmailSink`, `parseEmailDeliveryEvent`, the email part of `getNotificationSinks`/`mockSinkFor` (now Slack only; `NotificationSink.kind` is `"slack"`), `MAGIC_LINK_WEBHOOK_URL`, `HULLWISE_EMAIL_API_KEY`, `HULLWISE_EMAIL_FROM`, `HULLWISE_EMAIL_WEBHOOK_SECRET` (never documented for deployment). The per-tenant alert email sink is therefore not a second sender any more: its role is taken by `queueEmail` on top of `EmailProvider`, and the only Resend HTTP code is `ResendEmailProvider`. **Kept**: signed unsubscribe links and the one-click endpoint, `email_suppressions` and its page, preferences, `appBaseUrl`, `renderEmail`/`EMAIL_STRINGS` names.
- **Console** `/admin/email`: provider state and sender, webhook state, last-7-days counts (each opens the filtered log), the log with filters (status, template, tenant or platform, full recipient matched by hash), a "send test email" form (platform `test` template, audited `email.test_sent`), the platform suppression list with an audited remove, and the setup guide. **Guide**: `integration_guide.email` (Resend account, sending domain, SPF, DKIM, DMARC, sending-only key, Railway variables, webhook, test; vendor-dependent steps with the "To verify" badge), shown in the console and as a super-admin-only tab of Integrations → Guide. **Dev inbox** `/dev/emails`: the mock's captured emails with a sandboxed HTML preview and the text part; 404 unless `NODE_ENV` is development (or test).

**Alternatives.** Storing the payload (encrypted) in the log row, or in an outbox table, so the tick could resend without pg-boss (rejected: the log must never hold links; live mode always runs the worker, which is durable; only demo/dev processes can lose an in-memory job, and the sweep reports it). Hashing recipients with plain SHA-256 (rejected: dictionary-reversible); keyed hash means rotating `APP_ENCRYPTION_KEY` makes old hashes unmatchable (accepted: rotation is rare, suppressions can be re-added). Copying provider bounces into each tenant's `email_suppressions` (rejected: needs the address in clear in the event; the platform list covers every tenant). Keeping strings in code (rejected by the issue: translation files). A dev inbox reachable in production behind a flag (rejected: on a public mock-mode demo it would expose sign-in links). Rendering at delivery from stored props (rejected: props carry links).

## 2026-10-01 · Backorders end to end (#26): hold, PO link, platform hold, release

**Decision.**
- **When.** A new order is checked against stock at import (`importOrder`, any source, `outcome = created`), and the replacement order of an edit (#22) after the replaced orders gave their stock back. Lines already waiting are skipped, so the check is idempotent. Existing orders are not checked retroactively (a backfill of an old shop would hold half of it). Tenant settings `backorderHold` (default on) and `backorderPlatformHold` (default on), edited from Settings → operational.
- **Stock model** (`packages/core/src/backorders.ts`, pure). `available` is the platform's number (free for new orders, already net of committed units), summed over locations. A level read *before* an order was placed does not reflect it: the order takes from `available` minus the units of earlier orders the level does not reflect yet (net of their own backorders). A level read *after* the order was placed already took the order's units out; the only trace of a shortfall left is `committed > on_hand` (minus units other backorders already account for). Negative levels are stored as zero (sync rule), so without on hand/committed (the mock) a reflected order is never backordered. Shortage = what stock cannot serve; only that goes on the backorder (partial lines keep the rest).
- **PO link.** The earliest expected incoming PO line (`confirmed`, `in_transit`, `partially_received`; undated last) whose unclaimed units (ordered − received − other open backorders on that line) cover the whole shortage. None → `pending` without a PO; a re-check links one later (PO confirmed, edited, new). Status `covered` = linked to an incoming line.
- **Hold through the state engine.** `deriveOrderStatus` gained the fact `awaitingStock` (an open backorder exists), applied after hard facts, manual decisions and shipments, before tenant rules: `on_hold` with reason `hold:awaiting_stock`. `recomputeOrderStatus` reads the fact; no tag is involved. The rules preview passes the fact too. A manual status still wins (an operator decision sticks), the proper way out is "cancel wait".
- **Platform hold.** Two outbox kinds, `order.fulfillment_hold` and `order.fulfillment_release`, asynchronous. Keys: the hold by its episode (`order.fulfillment_hold:<order>:<first backorder id>`), the release by the hold it lifts (`order.fulfillment_release:<hold write id>`), so hold → release → hold is three writes and a repeated release is one. `CommercePlatform.holdFulfillment / releaseFulfillment`: Shopify holds each open fulfillment order with reason `INVENTORY_OUT_OF_STOCK` and the handle `hullwise-awaiting-stock`, and releases only holds with that handle (a merchant's own hold survives). Needs `read/write_merchant_managed_fulfillment_orders` (added to `core.orders` scopes; the handle and multiple holds per fulfillment order need API 2025-01+: to verify on a real store). Mock keeps holds in memory (`fulfillmentHoldOf`).
- **Release.** `refreshBackorderCoverage(variants)` (receipt, PO confirm/cancel/edit, the safety tick): free units = Σ available − units still owed to unreflected orders; first fit in age order (oldest first, one that does not fit does not block a smaller younger one). Released backorders become `fulfilled`; an order with none left open gets `hold_released` (reason `stock_available`), a status recompute, the platform release, and a `stock_available` notification to its assignee, or to owners/admins/operations when unassigned. Unreleased ones are re-linked if their PO line went away. The safety tick `backorders` runs every 10 minutes (minutes 7, 17, …) for tenants with open backorders; its release writes go out with the `writes` tick.
- **Other exits.** Cancel wait (action `change_order_state`): open backorders `cancelled`, `backorder_closed` event with author, note and diff, release as above. Order cancelled (Hullwise or platform) or replaced: open backorders `cancelled`; fulfilled on the platform: `fulfilled` (no platform write, the platform already moved on).
- **Views.** `stock=awaiting` (open backorder) and `stock=ready` (all open backorders covered by current stock, i.e. released at the next re-check, or released and still not shipped: status new / pending review / confirmed) in `orderListWhere`, so the page, CSV export and saved views share them; chips with counts on the orders page.
- **Stock check card** and **option grid** read the same numbers: available and committed are Σ inventory levels, incoming is Σ (ordered − received) of incoming PO lines. The grid lays out any two options (picked by the user), sums the others inside each cell, appends values only variants carry; its totals equal the levels by construction (tested in core and on the seed).
- **Dashboard tile** (kept small for #43): orders/units waiting for stock, and the top variants by units sold in 30 days with available ≤ the tenant's low-stock threshold.
- **Seed.** Backordered demo orders are open (new / pending review / confirmed, not partially fulfilled), held (`on_hold`, `hold:awaiting_stock`) with the `backorder_created` and `status_changed` events, and their variant is out of stock (those orders took what was left); each tenant has at least one waiting order covered by an in-transit/confirmed PO line (a line is appended to an incoming PO when the random data has none).
- Indexes `backorders(order_id, status)` and `backorders(purchase_order_line_id)` (migration 0026, additive).

**Alternatives.** A tenant state rule with an `awaitingStock` condition instead of the built-in fact (rejected: existing tenants would need a data migration to get the rule, and a missing rule would silently ship backordered orders). Comparing the order to `on_hand − committed` everywhere (rejected: Hullwise's own receipts and the mock do not move `committed`; the clamp makes it unreliable). Strict FIFO release (rejected: one large old order would block every small one behind it). One `order.fulfillment_hold` kind with a boolean (rejected: kinds read better in the outbox list and the release must reference its hold). Linking backorders to draft or sent POs (rejected: only confirmed POs are incoming everywhere else in Hullwise).

## 2026-10-02 · Inventory control (#30): adjustments, stock-takes, unexplained losses, markdowns

**Decision.**
- **Adjustments** (`adjustStock`, packages/services/src/inventory/control.ts). Reason codes `damaged | lost | found | count_correction | other` live in a new nullable column `inventory_movements.reason_code` next to the existing `reason = 'adjustment'` (no new reason values, so every reader of movements keeps working). `validateAdjustment` (core) enforces the direction (damaged/lost remove, found adds, the others either way), a note for "other" and no level below zero at the location. The level row is locked, written, the movement and an audit entry (`inventory.adjusted`, diff of the level at that location) are written in the same transaction, then the new **absolute** level goes out as `inventory.set` through the outbox (dispatched by the action after the commit). A positive adjustment calls `refreshBackorderCoverage` so waiting orders are released. A delta write (Shopify `inventoryAdjustQuantities`) would be more robust against a sale landing between Hullwise's read and the write; `inventory.set` was kept because it is what the brief and every other stock write use, and because a Hullwise `inventory.set` still in flight already protects the level from being overwritten by a sync (`unconfirmedWriteTargets`).
- **Stock-takes**: tables `stock_takes` (number per tenant, location, `open | applied | cancelled`, who/when applied, movements written) and `stock_take_counts` (variant or null for an unknown code, the code typed, counted, plus `expected_at_apply` / `applied_delta` snapshots). A code matches SKU first, then barcode, case-insensitive; `add` counts N more (a scan is +1), `set` replaces. The review (`reviewStockTake`, core) compares counts with the **current** level at the location while the session is open (sales during the count move the expectation with them) and with the snapshot once applied. Applying locks the session, writes one `adjustment / count_correction` movement per difference (one insert, same timestamp, `reference_type = stock_take`, `reference_id = session`), sets each level to its count, enqueues one `inventory.set` per difference, re-checks backorders for raised variants, and writes a single audit entry (`stock_take.applied`, diff per variant, `batchId` = session id). Uncounted variants and unknown codes are never touched. The scanner input queues scans client-side and never disables its submit button (a disabled default button blocks Enter, which drops fast scans).
- **Unexplained losses** read `inventory_drift` (#24): rows of kind `unexplained` or `not_reported` with a negative delta, detected in the period (`driftLossUnits` in core), summed per variant and valued at the variant's current cost. A deduplicated row counts once whatever its `occurrences`. Because the platform retention (14 days by default) would make a monthly report impossible, the purge now keeps those loss rows for `INVENTORY_LOSS_RETENTION_DAYS` (400, packages/config); other drift keeps the platform window. Alternative rejected: copying losses into `inventory_movements` from the sync path (changes #24's write path and double-counts with drift).
- **Markdowns**: `suggestMarkdown` (core, pure) suggests a compare-at markdown for active variants with stock and no sales in the lookback window or cover ≥ `slowCoverDays` (30 %), or cover > `excessCoverDays` (15 %); depth constants in `MARKDOWN_DEPTHS_BPS`. The base is the compare-at price when the variant is already marked down. **Floor**: new tenant setting `markdownMinMarginBps` (default 2000 = 20 %, Settings → operational); minimum price = ⌈cost / (1 − m)⌉ on the net-of-tax price, grossed up with the home-country rate when prices include tax (`marginFloorPrice`), cost from #23. No cost → no suggestion (the floor cannot be honoured). An exhaustive sweep test proves no suggestion is ever below the floor. Applying runs through `runBatch` (one transaction per variant): the suggestion is **recomputed inside the record's transaction** (a stale or tampered selection, or a floor raised meanwhile, is skipped), price and compare-at are written, a `variant.prices` outbox write is enqueued (asynchronous, retried, supersedes), audit `variant.markdown_applied` per variant and `bulk.variant.markdown` for the batch.
- **Price history**: no history existed, so a small additive table `price_changes` (variant, price and compare-at before/after, `source = markdown | bulk | manual`, batch id, actor). It is written by markdowns, by the bulk price/compare-at edits (`updateProductPricesWithPlatform`) and by the single price edit on the product page; platform-side price changes read by the sync are not recorded (the audit log never had them either). Audit diffs alone were rejected: keyed by variant title, per product, not queryable per variant.
- **Permissions**: everything sits on the `inventory` page (read: everyone who can see inventory; write: owner, admin, operations); applying markdowns also needs `products` write. No new action keys.
- **UI**: `/inventory/stock-takes` (+ detail with scanner and review), `/inventory/markdowns` (selection and bulk apply, recent markdown history), `/inventory/losses` (period and location), an "Adjust stock" dialog on each inventory row and on the product page, reason codes on the product's movement list, a price history card on the product page. Migration 0029 (three tables with RLS, one nullable column).
## 2026-10-02 · Account emails and flows (#52): invitations, forgotten password, verification, security notices

**Decision.**
- **Invitations** are a tenant table `invitations` (tenant, normalized email, role, optional suggested name, inviter, `token_hash`, `expires_at` = 7 days, `status` pending | accepted | revoked, send count, accepted/revoked by and at), RLS like `tenant_memberships`. No HTTP surface. Alternative rejected: an inbox endpoint enabled by a flag in production (a mock-mode demo would expose sign-in links).

**Alternatives.** Invitations as a platform table without RLS (rejected: the Users page would need the admin connection for tenant data). Embedding the tenant id in the token to look it up inside `withTenant` (rejected: the auth layer already reads memberships with the admin connection; the token would grow and leak the tenant id). Reusing `verification_tokens` for resets (rejected: no place for the rate-limit rows of unknown addresses nor for used/invalidated states).
## 2026-10-02 · Payments and money (#27): manual payments, partial refunds, actual fees and payouts, tax report

**Decision.**
- **Ledger.** New table `order_transactions` (kind `manual_payment` | `refund`, amount, method, date, note, refunded lines with restock flag, platform refund id, amount requested when the platform accepted less, author). The order row keeps the totals the rest of Hullwise reads (`refunded_minor`, `payment_status`); the ledger is what is behind them. `payouts` and `balance_transactions` (unique per tenant, provider, external id; transactions linked to the payout and, by external id, to the order) hold the processor's view. Migration 0027, additive.
- **Manual payment** (`recordManualPayment`, action `record_payment` on the orders page level): only on payment `pending`, not cancelled or replaced. Partial amounts are allowed: the order stays `pending` with the rest outstanding and becomes `paid` when the manual payments cover the total (no new canonical `partially_paid` status: the canonical payment statuses stay as in CLAUDE.md §4). The order's payment method is not changed; the method received is recorded on the transaction. Platform write `order.mark_paid` through the **outbox** (asynchronous, keyed `order:payment:<transaction>`): Shopify `orderMarkAsPaid` for the whole balance, `orderCreateManualPayment` for a part (to verify on a real store). Event `payment_recorded` (author, diff), status recompute, audit in the action.
- **Partial refund** (`refundOrder`, action `refund_order`): only on `paid` / `partially_refunded`, amount ≤ total − refunded (`validateRefund` in core), optional lines (units not yet refunded) and optional restock at a location (default location when none is picked). **Synchronous** platform write `order.refund` → new `CommercePlatform.refundOrder`; Hullwise records the amount the platform accepted (capped by what was captured). `refundReturn` is kept on the interface (the `return.refund` kind and its test use it) but both adapters implement it by delegating to `refundOrder` without restock: one refund implementation. Restocked units: inventory movement `refund_restock`, level + quantity, and the line's current quantity − quantity (the cost of goods follows the goods). Units refunded without restock stay on the line (the customer keeps them, their cost stays in the P/L). Event `refund_issued`, status recompute when the payment status changes (a full refund → `refunded`, out of the sale scope). A per-dialog `requestId` makes a repeated request answer from the outbox record instead of refunding twice. The returns module adds these refunds to its own when it recomputes `refunded_minor` (previously `max(order, returns)` would have dropped a goodwill refund).
- **Default status**: `partially_refunded` with no fulfilment now falls back to `confirmed` like `paid` (money was captured), instead of `new`.
- **Actual fees.** `orderEconomics` takes `actualPaymentFeeMinor`; `orderEconomicsForPeriod` fills it with the sum of the fees of the order's balance transactions once a `charge` of the order was imported; otherwise the estimate (`paymentFeeBps` + fixed per method) applies. Every economics row carries `paymentFeeSource` (`actual` | `estimate`), the P/L totals split `paymentFeeActual*` / `paymentFeeEstimated*`, and the order list has the matching `feeSource=actual|estimated` filter (same rule), so the P/L note, the payment-method table and the order card link to the orders behind each number. Out-of-scope orders keep a fee of 0 in the P/L whatever the processor charged (unchanged rule).
- **Payouts import.** `CommercePlatform.fetchPayouts` / `fetchBalanceTransactions` (Shopify Payments GraphQL `shopifyPaymentsAccount.payouts` / `balanceTransactions`, fixtures marked "to verify"; a shop without Shopify Payments returns none and every fee stays an estimate). `runPayoutsSync` follows the other syncs: `sync_runs` row `objectType = payouts`, cursor (payout pages, then the transactions of each payout) saved after every page, paused at the time budget and resumed; a delta restarts a week before the latest payout because scheduled and in-transit payouts change. Queue `sync.payouts`, tick `payouts` daily at 05:20 UTC for connected Shopify tenants, "Sync payouts" button (owner/admin). Scope `read_shopify_payments_payouts` under `core.analytics`.
- **Mock payouts.** One deterministic generator (`buildMockPayouts` in `packages/integrations/src/mock/payouts.ts`) used by the mock adapter and by the seed, so a sync of the demo finds the same deposits: only processor gateways (`shopify_payments`, `apple_pay`, `google_pay`, `shop_pay`) are paid out; fees per order from a stable hash (EUR 1.5 % + 0.25 domestic / 2.9 % + 0.25 international; USD 2.9 % + 0.30 / 3.9 % + 0.30); refunds as negative transactions; an adjustment on about one deposit in twelve; daily payouts two days later, weekends to Monday, statuses scheduled / in transit / paid from the date. The mock reads the tenant's processor orders of the last 100 days and adds the refunds it made itself.
- **Tax report** (`taxReportForPeriod`) is built from the same economics rows as the P/L (sale scope, replaced orders out), so its tax column adds up to the P/L tax line by construction; a service test checks it against `pnlForPeriod` for both tenants over a month and a year, and the page shows the comparison. Rows by shipping country (tenant country when unknown) and **effective rate**: tax reported by the platform over the goods after discounts (net of tax when prices include it), rounded to 0.1 %; the tenant rate when the platform reported none. Tax on refunds is shown as information (the P/L tax line is the tax charged, unchanged definition). `NormalizedOrder` has no tax lines yet: an order with mixed rates shows its blended rate (to refine when the adapter maps tax lines).

## 2026-10-02 · Platform reliability (#32): watchdog, failure alerts, job history, tenant data export, audit retention

**Decision.**
- **Source status, one rule.** `sourceStatus` (core) decides the status of an `integration_health` row by precedence: `stale` (no success inside `freshness_minutes`, counted from the connection when it never succeeded) → `error` (3+ failures in a row) → `degraded` → `idle` (N successful runs in a row that wrote 0 rows; N per provider in `@hullwise/config`: Shopify 96 = a day of 15-minute deltas, Meta/Google 3 daily pulls, default 10) → `ok` (`unknown` if it never ran). `recordHealth` and the watchdog both use it, so a failed attempt after the window writes `stale`, not `degraded`, and the next tick does not flip it back. New column `zero_row_runs` (a run without a known row count leaves it alone). Event-driven sources (`*:webhooks`, `*:writes`) never go stale or idle: silence there means nothing happened.
- **Watchdog tick** (`watchdog`, every 10 minutes, `runWatchdog` per tenant in its RLS transaction): updates the status, asks for **one automatic resync per stale episode** (`resync_requested_at` older than the last success, or none; the handler maps the source to its pull with `resyncJobsFor`), and notifies owners and admins **at most once every 6 hours per source** (`watchdog_notified_at`; a stale source only once it is late beyond the tenant's existing `syncDelayGraceMinutes`; types `sync_delay` and `integration_health`/idle). Every automatic resync is audited (`integration.watchdog_resync`, system). It replaces `checkSyncDelays` of the hourly notify tick (removed, it sent the same notice). Alternatives: a resync every freshness window (rejected: if a resync does not fix it, e.g. an expired token, more resyncs do not either and the issue asks for one), clearing the notification clock on recovery (rejected: a flapping source would notify more than once in 6 hours).
- **Platform failure alerts** (`platform_alerts`, one row per signature `kind:tenant|platform:subject`): a job type failing `JOB_FAILURES_BEFORE_ALERT` (3) runs in a row for the same tenant (`job_failure`), or a stale source (`sync_stale`, raised by the watchdog tick). Raising again bumps occurrences; notifications go out at most once per `FAILURE_ALERT_WINDOW_HOURS` (6), claimed with a conditional update so two workers notify once. For stale sources the tenant side is the watchdog notice to owners and admins, so owners are not told twice. A success of the same job, or the source no longer stale, resolves the alert (`resolved_by = auto`); a super-admin can close one by hand (audited).

Recording never breaks a job. **Run now** (console): ticks and per-tenant pulls only (`runNowJob`), queued with the super-admin in the payload, or run after the response when no worker is deployed; audited `admin.job_run_now`. History follows the platform retention window (`HULLWISE_RETENTION_DAYS`). Tenant health (#48) now counts failed job runs of the last 7 days instead of the stand-in (failed sync runs, webhooks, writes); the console's integration counts include `stale`.
- **Tenant data export** (`tenant_data_exports`, tenant table): an owner (new owner-only action `export_tenant_data`; an impersonating super-admin acts as owner and is audited as impersonation) or the super-admin from the tenant page starts a background job (`tenant.export`). It reads **every table that carries `tenant_id`**, derived from the Drizzle schema (a new table is exported without code changes), inside the tenant's RLS transaction plus an explicit `tenant_id` filter, keyset-paginated on `id`, one CSV each (UTF-8 with BOM, header = column names, JSON as text, same formula-injection guard as the list exports) and a `manifest.json` (tenant, row counts, excluded columns), zipped by a small writer on `node:zlib` (no new dependency). Excluded: binary columns (logos, photos, attachments), secrets (`*_encrypted`, `secret`, `*token_hash`, `*_token`, `token_hint`, password) and earlier list-export files. The zip is stored in the row until `expires_at` (`TENANT_EXPORT_TTL_DAYS` = 7), then the nightly retention tick deletes the file (status `expired`, the row stays). Download links require the signed-in owner (or the super-admin) **and** an unexpired export, rather than a bearer token in the URL: a leaked link is useless. Request, completion and every download are audited. **No deletion flow**: removing a churned tenant is irreversible, cascades through every table and needs its own confirmation and legal checks; the console now points churned tenants past retention to the export, and deletion stays manual.
- **Audit retention per plan**: `auditRetentionDays` on each plan (Starter 180, Growth 365, Scale 730 days; platform rows `PLATFORM_AUDIT_RETENTION_DAYS` = 730; an unknown plan keeps the longest window). The nightly retention tick deletes in batches of 5,000 rows (`delete … where id in (select … limit n)`, short statements), on the admin connection (tenants can never delete audit rows), leaving one `job_runs` row per tenant (`audit.retention`: rows = deleted, batches, cutoff, window) and, when something went, one audit row `audit.retention_purged`.
- **Audit viewer filters**: `parseAuditFilters` / `auditFilterConditions` (services) shared by the owner's audit page and `/admin/audit`: actor (member, or email part on the console), actor type, entity type, record (entity id), action prefix, date range in whole days of the viewer's time zone (tenant time zone for owners, UTC on the console). The entity cell links to the history of that record.
- **Dashboard widget**: one component, `SourceHealthWidget`, on the tenant home: sources of connected integrations not OK out of the total, with the worst five; hidden for roles that cannot open Integrations.

**Alternatives.** A separate run table per job family (rejected: one table, filtered by job type, is what the console needs). Storing export files on disk or object storage (rejected for now: the platform has no object store; the bytea column works for demo-sized tenants and is purged after 7 days; to move when a store exists). Hard-coded table list for the export (rejected: it would silently miss new tables).

## 2026-10-02 · Platform MCP server (#21): AI clients connect to a Hullwise tenant as one person

**Decision.**
- **Transport.** Remote MCP over Streamable HTTP at `POST /api/mcp`, served by `apps/web` with the official TypeScript SDK (`@modelcontextprotocol/sdk` 1.31). Stateless: one `Server` + `WebStandardStreamableHTTPServerTransport` per request with JSON responses (`sessionIdGenerator: undefined`, `enableJsonResponse: true`), so any number of web instances serve it and nothing lives in memory; `GET`/`DELETE` answer 405. The SDK's low-level `Server` is used on purpose (the SDK marks it for advanced use): the tool list depends on the token, input is validated with the tools' own zod schemas and refused calls must be logged with their reason, which `McpServer.registerTool` does not allow.
- **Auth.** OAuth 2.1 per the MCP authorization spec: RFC 9728 protected-resource metadata (`/.well-known/oauth-protected-resource` and `/…/api/mcp`), RFC 8414 server metadata (`/.well-known/oauth-authorization-server`), both rewrites to `/api/oauth/*`; the 401 carries `WWW-Authenticate: Bearer resource_metadata=…`. Dynamic client registration (RFC 7591) for **public clients only** (`token_endpoint_auth_method: none`, PKCE S256 mandatory, no client secrets): redirect URIs https, loopback http (any port on match, RFC 8252) or a private-use scheme; 20 registrations per IP hash per hour. Authorization code (single use, 5 min, bound to user, tenant, client, redirect URI, PKCE challenge and resource), refresh with rotation and **reuse detection** (presenting a replaced refresh token revokes the grant), RFC 7009 revocation, `iss` in the redirect. Consent at `/oauth/authorize` on Auth.js users (login redirect with `next`; `safeNextPath` cap raised from 500 to 2048 characters for the authorize URL): the person picks one workspace where MCP is available and can untick scopes. Personal access tokens as fallback (profile → Connections), `kpat_` + 32 base62 characters, shown once, 30–365 days, max 10 active per person and workspace, rotation keeps the row. All secrets (`kpat_`, `kat_`, `krt_`, `kac_`) are stored as **HMAC-SHA256 with a server pepper** (`MCP_TOKEN_PEPPER`, else derived from `AUTH_SECRET`) plus a display prefix; rows carry `expires_at` and `rotated_at`, always one user + one tenant.
- **Where tokens live.** Token, code, log, rate-bucket and proposal tables are tenant tables under RLS. A bearer token arrives before the tenant is known, so only the lookup by hash goes through the admin connection (the auth layer, like invitations and `getTenantContext`); every write after it runs in `withTenant` on the app connection. `oauth_clients` is a platform table (a client belongs to no tenant until consent).
- **Authorization.** Every tool is a `HullwiseTool` declaring page, optional action and module, scope and effect; the server lists and runs a tool only when the token has the scope, the role passes the role × page × action matrix and the module (core or add-on) is on (`toolDenial`). Tools run inside `withTenant` as the person (`actor.type = "mcp"`) and call `packages/services` only. Add-on tools live in their package (`COD_MCP_TOOLS` in `@hullwise/addon-cod`, `module: "addon.cod"`) and the web app concatenates them; `list_customer_campaigns` needs `addon.customer_campaigns`; segment tools are core and show control groups only with that add-on.
- **Scopes.** `read` (always included), `write:notes`, `write:orders`, `write:campaigns`, `write:purchasing`. Unknown scopes are dropped; a refresh can narrow but never widen.
- **Privacy.** Results are masked by default with `maskPii` (core, recursive: emails `m***@domain`, phones `•••1234`, person names `Mario R.`, street, ZIP and IP `•••`, emails and phones inside free text; city and country stay readable). Full PII only when the tenant switches `mcpFullPii` on **and** the role is in `MCP_PII_ROLES` (owner, admin, operations, customer care): marketing and viewer always get masked data. Free text is sanitised (control and bidi characters, LIKE wildcards) and capped (80 for search, 1000 for notes, 500 for reasons). The request log never stores arguments or results.
- **Writes safe by construction.** Direct writes: `add_order_note`, `assign_order`, `set_order_status` limited to `MCP_ORDER_TRANSITIONS` (new/pending_review/confirmed/on_hold among themselves, fulfilling → on_hold). Proposals: `propose_order_cancellation`, `propose_refund` (≤ refundable), `propose_campaign_pause` (active Meta only), `propose_purchase_order` (validated like the form): a `mcp_pending_actions` row (7-day expiry, one pending row per action and record), a `mcp_proposal` notification to members who may approve, and the approval inbox `/t/[tenant]/approvals`, where approving runs the existing service as the approving person inside a savepoint (failure → `failed` with the error, nothing kept). Every write leaves an order event (`actor_type = mcp`, `metadata.mcpClient`) and/or an audit entry (`actorType: "mcp"`, user, client, token, diff); decisions are audited too.
- **Commercial gating.** Module `core.mcp` with `minPlan: "growth"` (`isModuleInPlan`), checked at every bearer resolution, at consent and at code exchange. Tenant opt-in switch `settings.mcpEnabled` (default **off**; the demo Northwind is on) and `mcpFullPii`; super-admin kill switch per tenant (`tenants.mcp_disabled_at/_note`, audited) and platform-wide `HULLWISE_MCP_DISABLED=1`. Gate failures answer 403 with a readable reason.
- **Limits.** Fixed one-minute windows in Postgres (`mcp_rate_buckets`), 60 calls per token and 300 per tenant per minute, counted on every POST; the limiter **fails closed** (any database error → 429 with `Retry-After: 5`). Max page size 50. Request log `mcp_request_log` (tool, user, client, duration, outcome, error code) also for failed authentication (tenant null when the token is unknown, written with the admin connection), 403s and 429s.
- **Shared tool layer.** `packages/services/src/tools` holds `HullwiseTool`, the runtime, `toolDenial`, JSON-schema export and helpers. The assistant's seven analytics tools were moved onto it (same names, descriptions and citations; `assistantToolsFor` now uses `toolAllowed`) and are part of the MCP list (`MCP_CORE_TOOLS` = assistant tools + 10 MCP read tools + 7 write tools). Citations become `source: { period, filters, link }` with absolute links for MCP clients.
- **UI.** Profile → Connections (server URL, own connections with last use, revoke/rotate, PAT creation, guides), Settings → AI & MCP (owner/admin: switches, server URL, guides for Claude, ChatGPT, Cursor with "To verify" badges on vendor-UI steps, every connection of the workspace with revoke, 7-day activity), approvals inbox, console `/admin/mcp` (usage per tenant over 30 days, kill switch; nav entry left to the orchestrator). Approvals and the AI settings page are linked from each other and from the notification; no tenant nav entry was added.

**Alternatives.** Stateful sessions (rejected: in-memory per instance). `McpServer.registerTool` (rejected, see above). Confidential clients with secrets (rejected for v1: MCP clients are mostly public/native; PKCE is mandatory anyway). JWT access tokens (rejected: revocation and the kill switch must take effect at once; a hash lookup per request is cheap). Plain SHA-256 for tokens (rejected by the issue). An in-memory rate limiter (rejected: per instance, and it cannot fail closed meaningfully). Letting writes like cancel or refund run directly with a "confirm" argument (rejected: a model can set any argument; a person must approve in Hullwise).

## 2026-10-02 · Customer campaigns, remaining work (#34): approval, scheduling, asynchronous send queue, frequency cap, shared suppression, measurement lock, sequences, new segment fields and insights

**Decision.**
- **Workflow and approval** (add-on `addon.customer_campaigns`). One-off: `draft → pending_approval → approved → scheduled → sending → sent`; sequence: `draft → pending_approval → approved → active ⇄ paused`; "back to draft" from any state that is not delivering, and content is editable only in draft (pure transition table in `packages/core/src/customer-campaigns.ts`). Who approves is the role matrix: new action `approve_customer_campaign` mapped to write level on `customer_campaigns` (owner, admin, marketing today); the author — who created **or** submitted the campaign — cannot approve it unless owner (`canApproveCampaign`). Sending back requires the same permission and a note. Notifications through #33: new type `customer_campaign` (in-app by default, email optional, add-on-only), to every approver but the author on submit and to the author on approve/send back/sent; the bell renders them from `notifications.rendered.customer_campaign_*`.
- **Manual campaigns** ("sent from another tool") skip approval: Hullwise sends nothing, so "Record as sent" snapshots the groups at once (same exclusions). Alternative rejected: approving a campaign Hullwise does not send.
- **Scheduling and send window.** The scheduled time is a wall-clock time in the store's time zone (or "as soon as possible"); the job starts the campaign at that time or at the next opening of the window `campaignSendStartHour`–`campaignSendEndHour` (tenant settings, default 09–20, DST-safe via `zonedWallTime`). A send that reaches the end of the window pauses and resumes at the next opening. The segment is re-evaluated and the groups fixed **at the start**, which is also the exposure time that opens the measurement window.
- **Asynchronous send queue.** Exposures are the queue (no new table): treated rows of messaging channels start `queued` with `idempotency_key = rc:<campaign>:<customer>:<channel>`. `processCampaignSend` follows the #24 outbox shape: claim a batch in a short transaction (campaign row lock with skip-locked so one worker per campaign, rows `sending`, `attempts + 1`), call the provider outside any transaction with the key, record `sent` / retry with backoff (1, 4, 16 min, max 4 attempts; rate limits stop the batch) / `failed`. A worker killed mid-batch leaves rows `sending`; after 5 minutes they are claimed again and resent with the same key, and the provider delivers them once (`MessagingChannel.sendMessage` gained an optional `idempotencyKey`; the mock answers a known key with the first message id). Throttle per tenant **and channel** (`campaignThrottlePerMinute`, default email 600, SMS 60, WhatsApp 60), counted over rows sent or claimed in the last 60 s under a per-tenant-channel advisory lock, so two campaigns on the same channel never exceed it together. Counters are recomputed from exposures, never incremented. pg-boss: tick `campaigns` every minute (start due, enrol sequences, one `campaign.send` job per delivering campaign, singleton per campaign), each job runs up to 25 s and is recorded in `job_runs` (#32). Without a worker the web runs the same tick and job inline on campaign page loads (`kickCampaigns` in `after()`), like the other queue pages; the campaign page refreshes itself while sending. Alternatives rejected: a separate `campaign_messages` table (exposures already are one row per customer and campaign, with the unique key), retries through pg-boss (they would resend whole batches).
- **Exclusions**, first matching reason, applied to both groups alike so the comparison stays fair: no consent → suppressed → over the frequency cap → open order (per-campaign switch, default on; open = `OPEN_STATUSES`) → in another campaign's measurement window → control group. The preview shows the counts by reason; the start stores them on the campaign (`exclusion_counts`); a sequence stores the members currently waiting by reason. Suppression and consent are checked again at claim time: someone who unsubscribes while a campaign is sending becomes `suppressed`.
- **Frequency cap**: nobody gets more than `campaignFrequencyCap` campaign messages (status sent, any channel, manual included) in `campaignFrequencyDays` days (default 3 in 14). Control-group exposures are not messages and do not count.
- **Measurement lock** (`campaignMeasurementLock`, default on): treated and control customers of any campaign whose window (exposure + attribution days, each exposure for sequences) is still open are kept out of other campaigns.
- **Suppression list shared with transactional email** (#51/#33): campaigns read the tenant list `email_suppressions` (category `marketing` or `all`; bounces and complaints always block) and the platform list `email_address_suppressions` (hard bounces and complaints by keyed hash). Phones join the same tenant table: new column `identity_type` (`email` | `phone`, default email), the existing `email` column holds the identity (E.164 for phones) — additive, no rename. "Never contacted on any channel": a customer is excluded from every campaign channel if **any** of their identities is blocked, bounces included (conservative reading of the issue; a dead mailbox also stops SMS and WhatsApp). The suppressions page accepts an email or a phone and offers the `marketing` category when the add-on is on. Alternative rejected: a parallel campaign-only list.
- **Test send** to internal users before approval (draft, waiting, approved, scheduled, paused): members of the store picked by id for email, a typed phone for SMS/WhatsApp; never an exposure; recorded on the campaign (`test_sent_at/by`) and in the audit log. Not mandatory for approval.
- **Sequences** (always-on, implemented rather than split): a sequence is a campaign of `kind = sequence` on a segment with a control group (`sequence_needs_holdout` otherwise); activation switches the segment to live updates and evaluates it; each tick inside the send window enrols members never exposed to the sequence (their segment group is the permanent holdout: stable hash per segment and customer, same group if they leave and come back) and queues the treated ones. One exposure per customer per sequence: no re-entry after a later purchase (follow-up if needed). Results are intention-to-treat over each exposure's own window; the window stays open while the sequence is active. Time-based entry (e.g. "120–150 days since last order") follows the nightly full refresh of live segments.
- **Segment fields** (core CRM, no add-on): `open_order` (boolean), `bought_in_window` (new type `day_window`, value `[from, to]` days ago, ops "has an order" / "has no order"), `bought_category` (category = product type, the only category concept of the catalog; optional `days` look-back — without it it matches `bought_product_type`, kept for existing segments), `dominant_option` (parameter `option` = any option name of the catalog; the value with the most units bought, ties to the first value in code-point order: SQL orders with `collate "C"`, core `dominantOptionValues` the same), `days_since_last_marketing` (days since the last delivered campaign message; null when never — always null without the add-on). Leaves gained two optional parameters (`option`, `days`) validated per field (`param` in the catalog). The SQL profile builds the costly columns only when a rule reads them (`extrasForRules`); a services test checks every new field (and a nested mix) counts the same customers in SQL and in memory, the profile's dominant option equals the core rule on the raw lines, and incremental evaluation agrees with the full one.
- **Segment insights** (core): top products, categories (product types), option values, average spend per member, AOV, orders per member, sales channels (`source_channel`) and reachability (email / phone with consent), on the segment page for every tenant.
- **Gating.** Every new page (`/segments/campaigns/settings`, the workflow on `/segments/campaigns/[id]`) uses `requirePage("customer_campaigns")` (404 on Harbor) and every new action `requireWrite`/`requireAction(…, "customer_campaigns")` (forbidden); the tick and the send job skip tenants without the add-on. The campaign settings page needs `manage_settings`. MCP `list_customer_campaigns` is unchanged (still add-on-only) and now also lists waiting, scheduled and active campaigns with their status.

## 2026-10-02 · Merchant subscriptions add-on (#67): analytics and operations layer, not a billing engine

**Decision.**
- **Hullwise is the analytics and operations layer on top of the subscription app the merchant already uses, never the billing engine.** It reads contracts, renewal charges and cancellations from Shopify Subscriptions, Recharge or Loop through a `SubscriptionProvider` adapter and sends customer-care actions back through it. Out of scope: charging cards, building or editing selling plans, the end-customer portal. Completely separate from Hullwise's own tenant billing (#53, Stripe), which was not touched (only the add-on's English product name was added to `BILLING_PRODUCT_NAMES`, since a priced implemented add-on enters the catalog automatically).
- **Add-on, not core**: `addon.subscriptions` (provisional price 149.00/month in `modules.ts`), page key `subscriptions` (operations and customer care write, marketing and viewer read). Pages, server actions, the webhook route, the job tick, widgets, MCP tools and the guide page check the add-on; the services refuse writes without it (`SubscriptionActionError("disabled")`).
- **Code lives in the core packages behind the module flag**, not in a `packages/addon-subscriptions` package: the add-on extends core flows (order import flags, reorder planning, the segment engine, the #24 outbox registry, the P/L split of orders) and the issue places the metrics in `packages/core` and the writes in `packages/services/src/writes`. Pure rules in `packages/core/src/subscriptions.ts`, services in `packages/services/src/subscriptions`, adapters in `packages/integrations/src/subscriptions`. Alternative rejected: a separate package that would have needed hooks into five core services.
- **Capabilities are explicit** (`canPause`, `canResume`, `canSkip`, `canSwap`, `canChangeFrequency`, `canReschedule`, `canCancel`, `canSendPaymentLink`); an action without the capability is neither shown nor accepted (Recharge's 2021-11 API has no pause, so Hullwise does not emulate one).
- **Care actions are synchronous outbox writes** (`runPlatformWriteNow`, kinds `subscription.*`, provider `subscriptions`, keyed `subscription:<contract>:<action>:<dialog request key>`): the local contract is rewritten from the provider's answer, never optimistically; the same confirmation sent twice reaches the provider once and writes one timeline entry (the request key is stored on the event). Each action writes a `subscription_events` row (author `staff`, actor, field diff `{from, to}`) and an audit row.
- **Data model** (one additive migration): `subscription_contracts` (status, price and normalized MRR, interval, next billing, activation/pause/end, cancellation kind + normalized reason code + raw text, origin order, renewals/skips, failing-payment state, recovery assignee and last contact, churn risk), `subscription_contract_lines`, `subscription_billing_attempts` (success/failed/pending, normalized decline reason with the provider message, the cycle key retries share, next retry), `subscription_events` (author customer/staff/system/provider), `subscription_cancellation_reasons` (the tenant's editable list; provider text is mapped by keywords, unknown text → `other`, raw text kept). Orders get `subscription_contract_id` (no foreign key, the contract tables belong to the add-on), `is_first_subscription_order`, `renewal_number` (0 = first order): set by the subscription sync from the origin order and the successful charges, and on order import when the app already reported the order.
- **Metrics** (pure, hand-tested): MRR movement is computed per customer between the instants before the period and at its end; a paused contract counts zero MRR, so a pause is contraction and a resume expansion, never churn; not live → live is new, or reactivated when the customer had a contract before. Churn = contracts ended in the period / contracts live at its start, split voluntary (customer) vs involuntary (the app ended it after failed payments). Survival cohorts by activation month in the store time zone, cell k = contracts still live k calendar months after their own activation among those old enough. Forecast = scheduled renewals of active contracts × the eventual success rate of settled billing cycles (retries included). Profit = the core `orderEconomicsForPeriod` of each contract's orders (net revenue after refunds and returns − product cost − shipping − payment fees, actual fees when known). LTV = realised profit per subscriber; acquisition cost = the first order's campaign spend per attributed sale order (null for unpaid channels).
- **Renewal stock**: units of the scheduled renewals per variant vs available + open PO lines counted from their expected date; the shortfall is the larger of the gap at the horizon and the deepest gap before a late PO arrives; suggestion rounded to the primary supplier's multiple and MOQ. `replenishmentPlan` merges it (`mergeRenewalDemand`) when the add-on is on, so the suggested PO quantity reaches reorder planning and the auto-drafted POs.
- **Churn risk per subscriber** reuses the CRM prediction model: base = 0.6 × survival at the subscriber's next renewal number + 0.4 × the customer's P(active) from `customer_predictions`, lowered by an open failed payment, recent skips, a pause (more after 30 days) and a lengthened frequency; classified with the tenant's CRM thresholds; stored on the contract by the add-on's tick (every 15 minutes, with the delta sync; complete reconcile at 03:xx UTC) so lists, segments and widgets read one value.
- **Segments**: six subscription fields (status, days paused, payment failing, renewals, days to next renewal, churn risk) in a separate catalog entry (`SUBSCRIPTION_SEGMENT_FIELDS` / `SUBSCRIPTION_FIELD_SQL`, spread at the end of the core maps to ease the merge with #34), hidden in the builder without the add-on; four ready-made segments open the builder prefilled. Win-back campaigns reuse `addon.customer_campaigns` on those segments (holdout and uplift already there); nothing was rebuilt.
- **Shopify Subscriptions caveat**: the contract scopes are `*_own_subscription_contracts`, so an app reads only contracts it created; contracts of the Shopify Subscriptions app need Shopify's approval for third-party access. Marked "Da verificare" in the guide and the adapter. The Admin API exposes no retry schedule (Hullwise shows the next retry only for Recharge and Loop). Every Recharge/Loop endpoint, field name and webhook signature scheme is written from public documentation and marked "to verify" until tested on a live account.
- **Seed**: Harbor Home gets the add-on (and a customer-care user `care@harborhome.demo`, needed to show the care flow); Northwind none. Own RNG (20261067), runs after every other seed step so the rest of the demo data is unchanged: a candle/cleaning refill line, ~400 subscribers over 12 months through the simulated Shopify Subscriptions app, a subscription price cut 6 months ago after which voluntary churn halves, renewals declined (card expired, insufficient funds, declined) and partly recovered by retries at +3 and +7 days, a few failing now (some followed up by care), pauses and skips, every charge's order flagged, and "Candle Refill · Fig" short for next week's renewals with a PO arriving too late.

**Alternatives.** Hullwise as a subscription billing engine (out of scope by decision). Inferring renewals from order tags (forbidden: no order meaning from hard-coded tags). Asynchronous care writes (rejected: the timeline would show a change the app may refuse). A separate add-on package (see above).

A receipt that arrives before the send commits creates the row by provider id; the send then merges into it. Known gap: a crash between Spoki's answer and the log write can send twice (documented, as for any provider without idempotency).
- **Webhook.** `POST /api/webhooks/spoki/<tenantId>/<token>`: the study shows Spoki only supports a shared secret (no HMAC), so the token is an HMAC of the tenant id with `APP_ENCRYPTION_KEY` (nothing stored); wrong token, malformed tenant or add-on off → 404. Events reuse `webhook_events` (source `spoki`), keyed by message id + status (Spoki resends the same message with each status: a replay is a duplicate, a new status is not; inbound messages by id). 200 at once, processing queued (`webhook.process` with `source: "spoki"`) or inline after the response; failures recorded on the event and retried by the new `whatsapp` tick (every 5 min, events older than 5 min, 5 attempts) and by "Retry failed" / "Replay" on the Integrations page, which now route Spoki events to their own processor.
- **Status precedence** (core `nextMessageStatus`): queued < sent < failed < delivered < read < replied, forward only; a failure after a delivery is ignored, a delivery after a failure wins. Inbound rows are `received`. A receipt for an unknown message with a phone is logged as `external`; without a phone it fails and is retried (the send may still be committing).
- **Replies.** Linked to the quoted message, else the last outbound to that number within `linkOrderDays` (30); campaign messages never link orders. The answered message becomes `replied`; an order gets a `whatsapp_reply` timeline event. Opt-out keywords (tenant setting, default `STOP`, `UNSUBSCRIBE`; matching ignores case, accents and punctuation, whole reply or the first words of a short reply) and the provider's `131050` error add the number to the shared suppression list (`addPhoneSuppression`, category `marketing`, source `spoki`, audited): WhatsApp and SMS campaigns skip it, transactional order messages still go.
- **COD (only inside `@hullwise/addon-cod`, only with both add-ons).** The COD card sends through the Spoki channel when the add-on is active and connected (the existing `sendCodMessage`, so attempts, `cod_messages` and the `cod_message` event are unchanged). The job runner passes hooks to the Spoki processor only when `addon.cod` is active too: receipts keep `cod_messages` in step (`applyMessageStatus`); replies go to `applyCodReply`: keywords in the COD settings (`messagingReplies.confirm/cancel`, defaults `yes, confirm` / `no, cancel`, Northwind's demo in Italian); a confirm reply records a `confirmed` attempt on channel `whatsapp` (platform first, like an operator's); a cancel reply **escalates** the item to an admin and never cancels (destructive actions stay human, as the risk flags). Anything else is only on the timeline. The old `/api/webhooks/cod-messaging` route stays for the mock channel.
- **Order notifications** (confirmed, shipped, delivered): each with its template and a switch, off by default. The `whatsapp` tick reads `status_changed` order events after a cursor (`spoki_settings.notified_until`, set to "now" when the row is created, so turning notifications on never messages past orders), sends forward moves only (core `orderMessageEventFor`), once per order and event (key `order:<id>:<event>`), with a `whatsapp_message` timeline event.
- **Campaigns** (with `addon.customer_campaigns`): `handleCampaignSend` gives WhatsApp campaigns the Spoki channel (template `campaign`, rendered message as `BODY`); the send queue, throttle, idempotency keys and suppression re-checks are the core's. `processCampaignSend` now passes `meta` (campaign, customer) so the log links them.
- **Data model** (migration 0042, additive, generated): `spoki_settings` (config jsonb, cached templates, sync time, notification cursor) and `spoki_messages` (direction, purpose, provider id, idempotency key, phone, customer/order/campaign links set null on delete, template, body as the customer reads it when the template text is known, status with time, error code/message, reply-to, sender). Both RLS + isolation tests, `ADDON_ONLY`. No contact or conversation table: the log answers every question of the first version; Spoki contact ids can be added when the chat link is needed.
- **Gating.** Server: `requirePage("whatsapp_settings")` (owner/admin), actions through `requireWrite`/`requireAction(... "whatsapp_settings")`, the route checks `tenant_addons`, the jobs iterate add-on tenants only and `handleSpokiEvent` no-ops without it, the guide page 404s, the MCP tool `get_whatsapp_messages` carries `module: addon.whatsapp_spoki`. Client: nav entry in the Platform section next to COD settings, integration card, order and customer message logs render nothing without the add-on.

## 2026-10-02 · Withdrawn conversions and several Meta ad accounts (#82)

**Decision — conversions after the purchase.**
- **Row model.** `conversion_events` gains `kind` (`purchase` default, `retraction`, `restatement`) and `value_minor` (the restated value). An adjustment's event id is the purchase's plus `:<kind>`, so the existing unique index (tenant, provider, event id) makes it one row per (order, platform, kind) without a new unique index (one on order id could fail on old rows whose event id changed when the order got its external id). A restatement is an absolute value: the same row is re-armed (pending, attempts 0) when a later partial refund changes the value; a retraction is final and marks a still-waiting restatement `skipped/superseded`.
- **Decision rules** are pure (`decideConversionAdjustment`, `isOrderWithdrawn`, `purchaseStillDue` in `packages/core/src/conversions.ts`): only a `sent` purchase is adjusted; cancelled, `cancelled|returned|refunded` status, `refunded|voided` payment or refunds ≥ total → retraction; refunds below the total → restatement to `sent value − refunded` (from the value sent with the purchase, else today's total). A purchase still queued when the order stops being a sale is skipped as `withdrawn` (nothing reached the platform, nothing to retract).
- **Vendor facts [to verify, "Da verificare" in the tracking guide].** Google Ads: `customers/{id}:uploadConversionAdjustments` with `RETRACTION` / `RESTATEMENT` (`restatementValue.adjustedValue`), matched by `orderId` (always sent with the purchase) plus `gclidDateTimePair` when there is a gclid, `partialFailure: true`; an adjustment may be refused while Google has not processed the conversion yet: the row retries with the existing backoff (5 min × 2ⁿ, six attempts). Meta Conversions API documents no way to withdraw or restate a sent Purchase; sending a custom "Refund" event or a negative value would be counted as a new conversion or refused, so Meta adjustments are logged `skipped/unsupported` (no call). `CONVERSION_ADJUSTMENT_SUPPORT` holds this per platform; changing it is one line when Meta adds a mechanism.
- **Triggers, not polling.** `queueConversionAdjustments(ctx, orderIds)` is called by the order paths that cancel or refund: `recomputeOrderStatus` when the status becomes non-sale or `returned_partial` (covers in-app cancel, bulk, COD, manual status), `importOrder` when refunds, cancellation or payment status change (sync and webhooks), `refundOrder` and `applyReturnToOrder`. The `tracking` tick (every 5 min) runs `recheckConversionAdjustments` (sent purchases of the last 90 days whose order is no longer a full sale and has no retraction) before sending, as a safety net; "Run queue now" does the same.
- **Sending.** `sendDueConversions` sends purchases through `ConversionSink.send` and adjustments through the new optional `ConversionSink.adjust`; a sink without `adjust` marks the rows unsupported. Same batch, statuses, backoff and "Retry failed" as purchases. The log (tracking page, now a `DataList`) shows the kind, the restated value and a filter "Retractions and restatements"; the stats line counts adjustments sent and unsupported.

## 2026-10-02 · Public REST API v1 and outgoing webhooks (#81)

Rate limits reuse `mcp_rate_buckets` with `api:` buckets (120/min per token, 600/min per tenant, fail closed, 429 + `Retry-After`). Every authenticated request is logged in `api_request_log` (route pattern, status, error code, duration; never query values or bodies), shown in Settings → Developers.
- **PII consistent with MCP**: masked with `maskPii` unless the token has `pii:read` **and** the role is one of `MCP_PII_ROLES` **and** the tenant switched full customer data on (the existing `mcpFullPii`, now covering the API too). Order timeline diffs drop personal fields when masked.
- **Route registry** (`packages/services/src/api/routes.ts`): method, path, scope, page/action, zod query and body schemas, handler. The Next route `app/api/v1/[...path]` only calls the framework-free `handleApiRequest`, so tests drive the real HTTP layer with `Request` objects. The docs page renders `apiRouteCatalog()`; a web test fails if a route, parameter, scope, error code or event type lacks its text, or if the docs list a route that no longer exists. Rejected: an OpenAPI generator (new dependency, and the docs must be in three languages from the message files).
- **Outgoing webhooks.** Event types: `order.created`, `order.updated`, `order.status_changed`, `shipment.updated`, `return.updated`, `inventory.low_stock`, `product.updated`. Emitted in the change's own transaction from the services (transactional outbox: one `webhook_deliveries` row per subscribed active endpoint, nothing sent on rollback): the status engine `recomputeOrderStatus` (the only writer of `orders.status`), `importOrder` (created / updated with the changed fields; the initial history backfill emits nothing), local order edits, `importFulfillment` (new shipment or resolved status change), return creation and `applyReturnToOrder`, stock writes (`adjustStock`, `importInventoryLevel`, `applyInventoryLevels` except the full reconcile) when the variant's total crosses the low-stock threshold from above, product import (only when a receiver-visible field changed: the nightly reconcile rewrites every product), product edits, status, tags and prices. Active endpoints are read once per transaction (cache keyed by the transaction), so emitting costs one query when nobody subscribes. Payloads use the API resource shapes **without personal data** (receivers fetch the record with a token that may see it).
- **Delivery** through pg-boss queue `webhook.deliver` (dispatcher set by the worker; the web without worker delivers in process after the response, like emails), with a 2 s start delay and a "missing" retry for the emitting transaction to commit; the `webhooks` tick (every minute) re-queues anything due that was lost. Claim in a short tenant transaction (`for update`, `sending` lock 60 s), send outside any transaction, record in another. Signature: HMAC-SHA256 hex of `<unix ts>.<raw body>` keyed with the endpoint secret, header `Webhook-Signature: t=…,v1=…` (a second `v1` with the previous secret for 24 h after a rotation), plus `Webhook-Id` (delivery id), `Webhook-Event`, `Webhook-Timestamp`; no product name in headers. Secrets `whsec_…` are AES-GCM encrypted with the integrations helper and shown once.

Deliveries to customers' public endpoints are allowed in mock mode too (they are the customer's own systems, not vendor APIs); the seeded endpoints are paused on reserved `.example` hosts and no seeded delivery is due, so the demo and the e2e suite never call out by themselves.

## 2026-10-02 · Daily sales summary (core) and the accounting push add-on (#85)

**Decision.**
- **The summary is core, the push is an add-on.** `dailySalesSummary()` (`packages/core/src/daily-sales.ts`) and its page under Analytics (`/analytics/daily-sales`, day detail, CSV `analytics/export/daily_sales`) are for every tenant; everything that talks to an accounting system is `addon.accounting` (pages `accounting` = push log, journal per day and settings; actions; the `accounting` tick; the MCP tool `get_accounting_push_status`). Like `addon.subscriptions` it lives in the core packages behind its module flag (services `accounting/`, integrations `accounting/`), not in its own package: it extends core money flows and has no bespoke logic beyond the push. **Price: €69/month** (`monthlyPriceMinor: 6900`), between WhatsApp (49) and customer campaigns (99): A2X-style accounting syncs sell at a similar point and the live connectors are quoted on top.
- **What a day contains (money view, payment-agnostic).** An order is booked when it is a sale (the P/L sale scope plus `returned`/`refunded`) or when money was taken (`paid`, `partially_refunded`, `refunded`), never a replaced order; an unpaid cancelled order is not booked, a paid then refunded one is a sale and a refund. The sale and its payment fee go on the local day the order was placed (tenant time zone); each refund goes on the day it happened: order events that raised `refundedMinor` (Hullwise refunds, platform updates, returns), else the processor's refund transactions; the part of the refunded total no dated record explains goes on the placed day. Fees: the processor's actual fee once a charge was imported, else the tenant's rate (same rule as the P/L).
- **Columns follow the platform's sales report**: gross sales, discounts, refunds and shipping net of tax; tax net of refunded tax; `net sales = gross − discounts − refunds`, `total = net sales + shipping + tax` (what was collected), `net = total − fees` (what the processors owe). Integer minor units, exact splits (largest remainder) everywhere, so rows add up to days and days to the period by construction; a property test over random baskets checks it.
- **Tax rates without per-line rates in the model.** A line is taxed at the order's rate (tenant rate of the shipping country, or the rate the platform's tax implies when none is configured) unless its variant is `taxable = false` (0 %); shipping follows the order's rate; the platform's tax is spread over the parts by their theoretical tax. Rows are keyed `<country>|<rate bps>` like the tax report. Known approximation: with prices including tax and untaxed shipping, a few cents of tax move from goods to shipping (totals and per-rate tax stay exact).
- **Numbers link to a day page, not to the order list.** Booking on the refund day and the money-based scope cannot be expressed with the order list's filters (placed date, status), so every number of a day opens `/analytics/daily-sales/<day>` narrowed to the kind (sale, refund, fee), tax rate or method, listing the orders behind it with their contribution; each links to the order. Period-level cards are not links.
- **Journal**: credits sales and output tax per rate (mapped per rate or to the defaults), shipping; debits discounts, refunds, fees and the clearing account for the net; a negative amount changes side. Narration and line descriptions are English, like the Stripe product names: they are data for the accounting system, not UI.
- **Push gates** (pure `dayReadiness`): on or after the start day; closed in the tenant's time zone plus `closeDelayHours` (default 2 h, so late webhooks and refunds settle); every line mapped (an unmapped line alone, since the journal without it cannot balance); debits = credits; no order of the day with a Shopify `orders/*`/`refunds/*` webhook pending or failed, or with a platform write pending, running or failed. Days that fail a gate are stored `waiting` with machine-readable reasons rendered in three languages. A day with nothing to post is `empty` and never pushed.
- **Idempotency and versions.** One row per (tenant, day, version) in `accounting_journals`; the provider gets the idempotency key `tenant:day:vN`, so a retried or crashed run never creates a second journal; pushed/empty days are final for the tick; failed pushes back off 15 min × 2^n (max 12 h, or the provider's Retry-After). After a push the status is read back. **Re-push** (owners/admins, confirmation dialog, note, audit with the before/after) requires the day to reconcile now, voids the pushed journal at the system, keeps it as `voided` and pushes version + 1 from today's summary. Pushed days are not recomputed automatically: a change after the push (late refund, an order cancelled unpaid after being booked) is fixed by a re-push. Rejected: automatic drift detection (needs the seed and the service to load identical facts; a follow-up).
- **Provider.** `AccountingProvider` (chart of accounts, push one journal, read status, void) with `MockAccountingProvider` (generic chart, balance and account checks, idempotency keys, failure injection; ids it did not create but with its format count as existing, so seeded journals can be voided). Live connectors for Xero, QuickBooks Online and Fatture in Cloud are "available on request" in the guide (steps marked to verify), not built. The integration row is `provider = accounting`; health source `accounting:writes` (event-driven: never stale or idle).
- **Settings** in `accounting_settings` (zod `accountingSettingsSchema` in core: mapping, start day, look-back 1–90 days, close delay, journal status draft/posted) plus the cached chart; codes must exist and be active in the chart when one was read. Edited at `/accounting/settings` (Platform section, next to COD and WhatsApp settings); permissions: page `accounting` write for owners/admins, read for viewers, none for operations, customer care and marketing; connection actions also need `manage_integrations`.
- **Tick** `accounting`, hourly at :35 UTC (each tenant's days close at its own local midnight), only tenants with the add-on and operational; the transaction is held across the provider call like the subscriptions sync (in-memory mock; a live connector should move to short transactions like the outbox).
- **Seed.** Northwind gets the add-on (and its price in the seeded invoices), the simulated system with its chart, a mapping (IT on the defaults, DE/FR/ES on export accounts), start day 32 days back and a push log of the last 32 closed days: every day with sales pushed except the latest (failed, rate limited, next attempt in 30 min) and the one before (waiting: one of its orders has a seeded `order.update_details` write pending, rate limited); one older day shows a re-push (v1 voided, v2 pushed). Journals are built by the same core functions from the seeded orders. Harbor stays off and still has the summary.

**Alternatives.** Refunds on the placed day like the P/L (rejected: a refund after the day was pushed would never reach the books). Booking only the P/L sale scope (rejected: money taken on held or reviewed orders would be missing, and a refund of a cancelled paid order would have no sale). A per-line tax rate column on orders (no source fills it today; additive later). A separate `packages/addon-accounting` (no bespoke logic to isolate; the summary it needs is core).

## 2026-10-02 · Phone-width check over every route (#79)

**Decision.**

**Context.** Since 1 January 2026 Shopify no longer lets anyone create custom apps in the store admin; new apps come from the Dev Dashboard and give a Client ID and a Client secret only. Hullwise connected Shopify with a pasted `shpat_` token (now impossible for new stores) or with a platform-wide public app. The pinned Admin API version (`2025-07`) was out of support and Meta was on v21.0.

**Decision.**
- **Main path, self-serve:** the merchant creates their own app in the Dev Dashboard, releases a version with the scopes Hullwise lists, installs it and pastes shop domain, Client ID and Client secret on the Shopify card. The server runs the **client credentials grant** (store in the app's organization), checks the scopes, registers the webhooks, stores the credentials encrypted with the 24-hour token and its expiry, and starts the history import (#91, `startHistoryImport`). The adapter renews the token 5 minutes before expiry, or once on a 401, and then reports `token_expired` ("Shopify token refresh failed"); the factory stores a renewed token in its own short tenant transaction, not awaited, because the caller's transaction may hold the integration row.
- **Fallback, same app:** when Shopify answers `shop_not_permitted` (store outside the app's organization, e.g. an agency's app) or the app is not installed, the card shows "Install on your store" and the redirect URL to add to the app version: authorization code grant with the saved Client ID/secret (`integrations.config.app`, secret encrypted with `encryptJson`; no migration). The OAuth `state` is signed (`signState`: HMAC-SHA256 with `APP_ENCRYPTION_KEY`, tenant, user, shop, app, nonce, 10-minute expiry), so the callback no longer needs the state cookie and resolves the tenant on any host; the query HMAC is verified with that tenant's secret. The callback starts the history import when the installer's session reaches it; otherwise the connection is saved and Resync starts it (#91's rule for live stores without an import).
- **Advanced:** the platform public app (`SHOPIFY_API_KEY` / `SHOPIFY_API_SECRET`, same signed state) and the legacy pasted token ("Existing custom app, created in the Shopify admin before 2026").
- **Webhooks** are signed with the Client secret on every path (legacy: the API secret); `apiSecret` in the credentials is always the signing secret. Webhook registration now sends `uri` (the `callbackUrl` input field is gone from the current schema; `uri` exists since 2025-10).
- **Errors in plain words** from one map: `wrong_credentials`, `not_in_organization`, `not_installed`, `shop_not_found`, `version_not_released` (token without scopes), `missing_scopes` (required scopes missing: not connected, the message lists them and says "new version → release → approve in the store admin"), `token_refresh_failed`, `install_not_ready`, `unknown`. `shop_not_permitted` is documented by Shopify; the other body patterns are Da verificare on a live store.
- **Scopes:** `SHOPIFY_SCOPES_BY_MODULE` split into required modules (orders, shipments, catalog, CRM) and optional ones (discounts, returns, payouts, and the new `core.order_edits`: `write_order_edits`, `write_draft_orders`, which the order-edit and invoice mutations need and the list lacked). Test connection reports missing scopes required apart and per module.
- **API versions:** `SHOPIFY_API_VERSION = "2026-10"`, `META_API_VERSION = "v26.0"`, Google Ads stays v23. `API_VERSION_SUPPORT` (packages/integrations/src/versions.ts) holds the last supported day per platform (Shopify 2027-10-16; Google 2027-02-01 and Meta 2027-09-01, both Da verificare); a unit test fails once a date has passed.
- **GraphQL check (2025-07 → 2026-10):** every operation of the Shopify adapter was validated against Shopify's current Admin schema with Shopify's documentation tooling (schema validation only: no store, no credentials, no Hullwise traffic). Changed: webhook `uri` (above); customer `email`/`phone`/`emailMarketingConsent`/`smsMarketingConsent` → `defaultEmailAddress { emailAddress marketingState }` / `defaultPhoneNumber { phoneNumber marketingState }` (the mapper still reads the old fields). Still valid but deprecated, kept and Da verificare before they are removed: `Order.landingPageUrl` / `referrerUrl` (→ `customerJourneySummary.lastVisit`), `Location.isPrimary`, `ReturnLineItem.returnReason` (→ `returnReasonDefinition`), `Publication.name` (→ catalog title), `productDeleteMedia` (→ `fileUpdate`), `orderCancel(refund:)` (→ `refundMethod`), `OrderCancelPayload.userErrors`, `draftOrderComplete(paymentPending:)`. The tooling validates against the newest schema it has; a field that exists there exists in 2026-10 unless removed afterwards, so a live run on a dev store remains Da verificare.
- **Meta v26:** the fields Hullwise reads (campaigns, ad sets, ads with creative, daily insights with actions/action values, asset breakdowns) and the status writes are unchanged as far as the changelog says (Da verificare on a live account). Since v25 legacy Advantage+ shopping/app campaigns (`smart_promotion_type` `AUTOMATED_SHOPPING_ADS` / `SMART_APP_PROMOTION`) cannot be updated through the API and v26 pauses them: a pause/resume first reads the campaign type (best effort) and refuses with a readable message without writing; Meta's own refusal is mapped to the same message (its exact wording Da verificare).
- **One setup component for every card:** GA4's `IntegrationSetupGuide` (#86) is extended, not duplicated: optional step `titleKey`, `copy` as one or several values with `copyLabels`, `fields` (credential inputs, validated again on the server by `validateSetupFields`), `strategy` / `fallbackStrategy`, errors with `{detail}`. `SHOPIFY_SETUP` is the first definition with fields; `IntegrationSetupChecklist`, `IntegrationSetupError`, `IntegrationSetupFields` (apps/web/src/components/integration-setup.tsx) render it on the card and, with `variant="guide"`, on the guide page. Copyable values are resolved on the server (`resolveSetupValues`, apps/web/src/server/integration-setup.ts).
- **Privacy (GDPR) webhooks**, required for any app that may be distributed: one endpoint, `/api/webhooks/shopify/compliance` (API host: `/webhooks/shopify/compliance`), for the three topics. The signature is checked with the secret of the app the store is connected through (tenant credentials, saved app, or the platform app for stores without their own app); 401 otherwise, as Shopify requires. Each request is stored once in `webhook_events` (source `shopify_compliance`, platform ids only, no email or phone), audited, and becomes a console task: a platform alert of the new kind `compliance_request` on the alerts page. `customers/data_request`: the task asks to send the customer's data to the merchant (the Hullwise customer id is attached when found). `customers/redact`: the task asks to erase the customer (Hullwise has no automatic customer erasure yet). `shop/redact`: the Shopify connection is cleared at once (no credentials kept) and the task asks for the tenant's deletion through the lifecycle (churn, then the retention purge).
- **Mock mode:** Connect accepts any values and connects the simulated store (a store already simulated keeps its domain, a new one gets `mock-<slug>.myshopify.com`), then starts the history import. A Client ID containing `missing-scopes` simulates an app version without the order scopes, to show the error. The simulated store now reports every scope by default.

**Alternatives.** Token exchange (embedded app with App Bridge; rejected: Hullwise is not embedded in the Shopify admin). Keeping the cookie for the OAuth state (rejected: separate API host, and the signed state carries the tenant). A column or table for the app credentials and the token cache (rejected: the integration row's encrypted credentials and config already hold them; no migration). Shopify-initiated installs from a custom-distribution link without Hullwise's state (deferred: the merchant flow starts from the card). Automatic customer erasure on `customers/redact` (deferred: no erasure tool exists yet; a console task is safer than a half-erasure).

## 2026-10-02 · Go-live operations: key rotation, customer erasure, runbook, shared deployment (#88)

**Context.** The first real store goes live on the Railway deployment that also serves the demo. Replacing `APP_ENCRYPTION_KEY` made every stored credential unreadable, `customers/redact` only opened a console task, there was no backup/restore or onboarding procedure, and demo tenants on a live deployment would hand `.demo` / `example.com` addresses to the real email provider.

**Decision.**
- **Encryption key rotation with a window.** `APP_ENCRYPTION_KEY_PREVIOUS` (optional, validated at startup, warned about while set): `decryptSecret` tries the current key, then the previous one. `pnpm db:rotate-key [--dry-run]` (`packages/db/src/rotate-key.ts`, admin connection: a platform maintenance script, not tenant code) re-encrypts every payload only the previous key opens, listed in `ENCRYPTED_COLUMNS` (integration and ad-account credentials, the saved Shopify app secret and the pending Google sign-in token inside `integrations.config`, return bank details, webhook endpoint secrets) plus unfinished `email.send` jobs in `pgboss.job`. Row by row with a compare-and-swap on the old value, idempotent (a payload the current key opens is untouched), report with counts and `UNREADABLE` (exit code 1), one platform audit row. Without the previous key the same command only verifies: it closes the window and checks a restored backup.
- **HMAC-derived values** get a previous-key fallback where a verifier exists: Spoki and COD webhook URL tokens, unsubscribe links, the OAuth `state`, and email address hash lookups (`emailAddressHashes`: suppression checks at queue and delivery, campaign suppression, the console's recipient search). Their inputs are not stored, so they cannot be "re-encrypted": after the window old URLs and links are refused (documented: Spoki/COD stores re-paste the URL during the window), and the rotation script adds a new-key twin to each platform suppression whose address the database still knows (users, invitations, customers, tenant suppression lists). Password-reset rate-limit hashes and old delivery-log hashes are left to expire.
- **`customers/redact` erases automatically** (`redactCustomer`, packages/services/src/crm/redact.ts) inside the tenant's RLS transaction: personal fields of the customer and of its orders plus Shopify's `orders_to_redact` (guest orders), return bank details / customer note / custom answers, survey free text, conversion payloads, carrier-instruction addresses, WhatsApp/COD message recipients and bodies, COD risk profiles keyed on the phone or email, pixel identities and their checkout IPs, raw Shopify webhook payloads (replaced by `{"redacted": true}`, pending ones marked processed). Ids, amounts, dates, statuses, country and lines stay, so analytics and accounting do not move. Audited without personal data; no console task any more for this topic. Kept on purpose: tenant suppression entries (an opt-out must keep working), staff notes, timeline diffs, audit rows.
- **Demo addresses never reach a real provider**: at delivery, a provider other than the mock gets no message for reserved or demo domains (`example.com/net/org`, `.test`, `.example`, `.invalid`, `.localhost`, `.demo`); the row becomes `suppressed` with `reserved_domain`. Checked at delivery (not at queue time) so mock-mode tests and demos keep their full email log.
- **Runbook as two files**, `docs/ONBOARDING.md` (English, reference) and `docs/ONBOARDING.it.md`: one language per file reads better than two halves of one long page and each can be linked directly. The console links it under the tenant's setup checklist through `onboardingRunbookUrl(locale)` (Italian console → Italian file, otherwise English) built on `DEFAULT_DOCS_URL`, the repository's `docs/` on GitHub `main`, overridable with `HULLWISE_DOCS_URL`. The console's only users are the platform owner, who has repository access; the default URL names the repository, not the product, and GitHub redirects it if the repository is renamed.
- **Tenant hard deletion stays a documented manual statement** (`delete from tenants where id = …` as the admin role after export, cancellation, churn and a backup; every tenant table cascades), with a platform audit row written in the same transaction.

**Alternatives.** A key ring with key ids in every payload (rejected: changes the stored format of every secret for a rare operation; trying two keys is enough). Re-encrypting at read time (rejected: rows nobody reads would keep the old key forever, and the window could never close safely). Deleting the customer row on `customers/redact` (rejected: orders, returns and the P&L reference it; anonymising keeps the numbers right). Rejecting reserved domains at queue time (rejected: breaks the mock outbox the demo and the tests rely on). An in-app page rendering the runbook (rejected: the Next.js build does not ship `docs/`, and a console-only page adds auth and bundling for a document). A console button to delete a tenant (deferred: destructive, needs its own confirmation flow and Stripe cancellation; the cascade makes the manual statement safe enough for the first stores).
